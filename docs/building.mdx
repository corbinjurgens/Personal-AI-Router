# Building and Running NVIDIA Personal AI Router

This guide is for developers and users who prefer to compile Personal AI
Router (PAIR). To use a prebuilt Windows installer, Debian package, or binary
archive from the
[GitHub releases page](https://github.com/NVIDIA/Personal-AI-Router/releases),
refer to [Getting started](getting-started.mdx).

Run commands from the indicated project directory.

## Staged builds and Windows shortcuts

Settings > Service can select and preview an existing complete extracted GUI
build for the host platform and architecture. Windows expects `PAIR.exe` and
`resources/cli-bin`; macOS expects `NVIDIA PAIR.app` with its executable in
`Contents/MacOS` and services in `Contents/Resources/cli-bin`; Linux expects
`nvpair` and `resources/cli-bin`. Standalone `services/build/bin` output is not
a GUI bundle. Inspection checks paths, ownership and permissions, and refuses
unsafe paths or installer-owned targets. It executes no candidate code and does
not authenticate its publisher.

Build application is currently unavailable: production has no atomic acceptance
owner and refuses before Pause. Accepted transaction, helper, swap, restart,
recovery and semantic-readback cases remain unmet pending owner decision O1.
First deployment of a future apply-capable build requires a separate manual
rollout. Native installed application acceptance remains unverified.

On Windows, the GUI can create its per-user Start Menu shortcut. From the
repository, `scripts/pair-shortcut.ps1 create -AppPath <absolute-path-to-PAIR.exe>`
invokes the GUI's shortcut-only mode; `status` and `remove` are also supported.
Use an absolute path to a stable installed or unpacked executable. The command
does not start the service or open the normal window. An unrelated shortcut is
preserved. Native shortcut appearance and launch remain unverified.

## Prerequisites

Install these first:

- [Git](https://git-scm.com/downloads).
- [Node.js](https://nodejs.org/en/download) 25.5.0 or newer, which includes npm.
- [Go](https://go.dev/dl/) 1.25 or newer.
- [jq](https://jqlang.github.io/jq/download/) on your `PATH`. Install it with
  `sudo apt install jq`, `sudo dnf install jq`, `brew install jq`, or
  `winget install jqlang.jq`.
- On Windows, install the
  [latest Microsoft Visual C++ v14 x64 Redistributable](https://aka.ms/vc14/vc_redist.x64.exe)
  before using PAIR-managed llama.cpp from a source or services-only run.
  Release installers install it automatically. Microsoft's x64 package supplies
  both the x64 and ARM64 runtime binaries.

The reference Windows installer builds stage Microsoft's unmodified
Redistributable package. Redistributing that package is limited to licensed
Visual Studio users and remains subject to the
[Microsoft Software License Terms](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files).

## Quick Start from Source

Clone the repository, install dependencies, and start the application:

```bash
git clone https://github.com/NVIDIA/Personal-AI-Router.git
cd Personal-AI-Router/desktop
npm install
npm start
```

The `start` script generates desktop assets, compiles required Go executables
from sibling `../services` into `desktop/cli-bin/`, and starts Electron through
electron-vite. The service source is part of the same checkout, so there is no
submodule and no separate services build step.

The initial build can take longer than later ones. When the desktop
application opens, follow [Getting started](getting-started.mdx#2-complete-first-run-setup)
to install or select an engine, pair systems, prepare a model, and run a first
inference test.

## Make Targets

The `Makefile` at the repository root wraps the commands in this guide for
developers on Linux and macOS. Run these targets from there:

```bash
make          # list every target
make dev      # check toolchain versions, fetch Go modules, install npm packages
make build    # build the service binaries and the desktop bundles
make run      # start the desktop application in development mode
make check    # desktop gates: build scripts, lint, typecheck, contracts, tests
make test     # desktop unit tests plus go test in every services module
make clean    # remove build output; leaves installed dependencies alone
```

`make run` and `make build` install npm packages first whenever
`desktop/package-lock.json` is newer than `desktop/node_modules`, so a fresh
clone needs only `make run`.

`make test` includes the Go component and cross-process suites, which start
real subprocesses and bind local ports.

`make build-services` stages the standalone bundle described in
[Build the Services Alone](#build-the-services-alone). Run `make` for the
remaining single-step targets.

`make clean` removes generated build output and nothing else. It leaves
`desktop/node_modules` in place, along with the per-user data a run creates:
settings, logs, cluster identity, and any engine PAIR installed. To reset that
data as well, refer to
[Cleaning Up a Build from Source](#cleaning-up-a-build-from-source), which is the
quickest way back to a first-run state after testing pairing or engine installs.

Windows has no equivalent wrapper. Use the npm scripts and `build.bat`
described below.

## Build the Desktop Application Alone

Install dependencies and build the application bundles without starting them:

```bash
cd desktop
npm install
npm run build
```

Build only the service binaries bundled by the desktop:

```bash
npm run build:modular-binaries
```

The service source must remain available at `../services`. Target-specific
service-build scripts cover `win32`, `linux`, and `darwin` on x64 and arm64.
Refer to `desktop/package.json` for their names. The Go services use no cgo, so
you can build any of those targets from any host.

A local build produces an application you run on the machine that built it. Use
the [releases page](https://github.com/NVIDIA/Personal-AI-Router/releases) for
installable builds. This guide does not cover producing distributable artifacts.

## Build the Services Alone

The service scripts read `services/versions.json`, stamp each version, build 13
executables, and stage them together in `services/build/bin/`.

Linux and macOS:

```bash
cd services
./build.sh
```

Windows Command Prompt:

```bat
cd services
build.bat
```

Avoid building one component and then running an old staged bundle. Rebuild the
complete bundle so `services/build/bin/` is consistent.

## Offline copy baseline

These standalone commands are operator procedures, not first-launch hooks. Root
coordinates the exclusive interval while running as the profile owner. The full
procedure and refusal conditions are in the
[engine-manager reference](../services/nvpair-engine-manager/README.md#offline-copy-baseline).

```text
nvpair-engine-manager --initialize-fresh-profile
```

For a reviewed existing profile, use the separate amendment:

```text
nvpair-engine-manager --amend-copy-baseline --expected-journal-sha256=HEX --copy-baseline-disposition=complete-empty-history --attest-profile-quiescent
```

`HEX` is the lowercase SHA-256 of the exact reviewed journal bytes. Add
`--previous-profile-reviewed` whenever the previous app exists, even without a
journal. Add `--allow-empty-old-journal` only for a current version-1 object
missing only `copyRecoveryRequired`, with empty arrays and a valid boolean
`copiesComplete`. Strict current input requires empty arrays, incomplete
history and false recovery. Ordinary version-1 journals require both
`copiesComplete` and `copyRecoveryRequired`; missing journals remain
historically incomplete, old ordinary loads unreadable, and constructors do not
automatically provision or repair them. The old amendment is a one-off.

The current app path is `BASE/Nvidia Corporation/Personal AI Router` and the
previous app path is `BASE/NVIDIA Corporation/PAIR`. Their organization parents
can alias, so inspect app paths rather than the parent. On Windows both modes
require `LOCALAPPDATA` set, nonempty and absolute to the profile owner's Local
base, before mutation. Fresh allocation refuses either existing app, imports no
history and is non-idempotent. First GUI or headless launch can already create
the profile. Installation, reinstallation, empty inventories, deleted journals
and recreated children are not freshness evidence. Failure preserves allocated
and landed state. Unix success confirms file publication/readback and every
new directory entry through the first pre-existing ancestor. Windows has no
supported new-directory confirmation here: bounded success confirms allocation
and file publication/readback, reports `fresh-directory durability: UNVERIFIED (unsupported)`,
and does not establish whole-profile durability. Retain that limitation in
completion reports until support is separately verified.

Previous inspection accepts a definitely absent app or journal, a validated
empty current journal, or the precisely empty old shape without the current
old-input opt-in. Any previous marker, unreadability or inspection uncertainty
refuses even with the review flag. Preserve markers, including in partial
migrations. Retained downloads/copies, naming mismatch, current recovery true,
unreadable data and unsupported older shapes need separate review; replacement
documents are unsupported. Actual machine journal coverage is UNVERIFIED.

Root reserves the interval, prevents autostart/restart and other profile users,
closes GUI/TUI and stops service, broker and standalone owners using separately
authorized procedures. Root verifies controllers, destinations and downloads
stopped, reviews exact bytes and historical evidence in both namespaces, records
the digest and disposition, invokes the appropriate command once, checks backup
bytes, reported hashes and strict state, and resolves failures before release.
Empty live lists or markers do not establish history. The tool does not stop
owners. Sockets, service locks, optional ports and process snapshots cannot prove
quiescence; snapshots race startup and can miss renamed processes. Attestation is
mandatory and a nonempty `NVPAIR_SERVICE_ENDPOINT` is refused. Rechecks are not
atomic CAS against ordinary writers.

Amendment reserves a deterministic digest-named exact-byte backup and refuses an
existing backup. It rechecks hashes and reports observed landed state; refusal
or uncertainty exits non-zero. There is no automatic cleanup, retry, restore,
resume or persistent recovery protocol. A crash or uncertain write can leave
complete-looking bytes whose earlier durability error a later read cannot
recover. Preserve evidence and resolve state and durability before restart;
root enforces exclusion after the tool exits. After a separately authorized
interval is released, ordinary startup may reread the confirmed journal and
read-only evidence must show the expected baseline/source and remaining
blockers. Neither command establishes full owner evidence or build-apply
eligibility; O1 still refuses real starts, O2 external-root coverage remains
separate, and O3 does not certify predecessors or infer historical completion.

## Run Without the Desktop Application

After you stage `build/bin/`, you have a complete, runnable PAIR node without
the desktop application. How you drive it is up to you. You can start the
terminal interface, which is the quickest route, run the broker directly, or
write your own client against its API.

### Start with the Terminal Interface

This is the recommended way to use a services-only build, and the interface
intended for headless systems. `nvpair-tui` attaches to `nvpair-service`,
starting it if needed; the service owns the broker:

Linux and macOS:

```bash
cd services
./build/bin/nvpair-tui
```

Windows Command Prompt:

```bat
cd services
build\bin\nvpair-tui.exe
```

Pass `--service-path` if `nvpair-service` is not beside the `nvpair-tui`
executable. The terminal interface and desktop application can attach to the
same service at the same time.

[Using the PAIR terminal interface](terminal-interface.mdx) covers what to do
after it opens: pairing, engines, models, routing, and settings. It also lists
the operations that remain desktop-only.

### Run the Broker Yourself

Run `nvpair-ui-broker` directly when you want to drive the services
programmatically rather than through the desktop or terminal interface:

Linux and macOS:

```bash
cd services
./build/bin/nvpair-ui-broker
```

Windows Command Prompt:

```bat
cd services
build\bin\nvpair-ui-broker.exe
```

The broker speaks newline-delimited JSON-RPC on stdout and logs to stderr, and it
expects the worker binaries beside it. A programmatic client normally spawns it
with piped stdio. A quick check that it came up, on Linux or macOS:

```bash
cd services/build/bin
printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"ping"}' | ./nvpair-ui-broker
```

PowerShell:

```powershell
Set-Location services\build\bin
'{"jsonrpc":"2.0","id":1,"method":"ping"}' | .\nvpair-ui-broker.exe
```

You may see an `app:ready` notification alongside the response, and discovery may
be empty while LAN browsing starts. Set `NVPAIR_LOG_LEVEL=debug` or pass
`--log-level debug` for launch diagnostics. The accepted levels are `debug`,
`info`, `warn`, and `error`.

For the methods, notifications, and worker ownership, refer to the
[broker reference](../services/nvpair-ui-broker/README.md). That document, not
this one, is the source of truth for API usage.

### Inspect a Running Service

When `nvpair-service` is running, `nvpair-service diagnose` prints a short
local report: the service and broker process identities, the local policy's
activation, the bind state of each built-in engine facade, and resident model
configuration counts. Add `--json` for the same report as JSON.

Linux and macOS:

```bash
cd services
./build/bin/nvpair-service diagnose
```

Windows Command Prompt:

```bat
cd services
build\bin\nvpair-service.exe diagnose
```

The command never starts the service and reads only state the service already
holds. It does not send inference, wake an engine, or contact another machine,
so it does not show that inference or peer connectivity works. Fields, exit
codes, and limits are in the
[service reference](../services/nvpair-service/README.md#diagnosis).

### Write Your Own Client

The broker's JSON-RPC API is the same contract the desktop application and the
terminal interface use, and neither is privileged. If you want a different
interface, you can build one against that API rather than modifying PAIR. Drive
discovery, pairing, engines, models, and routing yourself, and let the broker
supervise the workers.

Start with the [broker reference](../services/nvpair-ui-broker/README.md) for the
protocol and lifecycle, and use
[the generated method surface](../desktop/docs/services-api.md) for the full list
of requests and notifications across the services.

If you are changing PAIR rather than only running it, the checks to run before
opening a pull request are in
[CONTRIBUTING.md](../CONTRIBUTING.md#development-setup).

## Measuring a released Windows GUI build

The optional `scripts/profile-windows-gui-build.ps1` observer records an explicitly
released build. It does not select a release revision, authorize a build or change
the default build commands. Dot-sourcing it only defines functions. Its tests use
tiny synthetic children, without building or starting PAIR:

```powershell
Invoke-Pester -Path scripts/tests/profile-windows-gui-build.Tests.ps1
```

For a required release, first obtain the exact source revision, serialized machine
interval, portable toolchain provenance, output disposition and cache mode. Use a
disposable clean source checkout and a new absolute evidence directory outside
every repository and synced vault. Do not use an installed application or a
retained accepted build as writable output. Never clear shared caches. A cold run
uses task-local empty dependency/output/compiler caches; it does not mean cold OS
disk cache. A warm run requires a later independently required release with the
same inputs. Otherwise report warm results as unmeasured.

Freeze an external UTF-8 JSON recipe and its SHA-256 before execution. Its fields
are `expectedHead`, `cacheState` (declared cache directories and known/unknown
warmth), `toolchain` (`node` and `npmCli` absolute portable paths), `inputs` (frozen
external script/input `path` and `sha256` pairs), and an ordered `steps` array.
Each step has a unique plain `name`, absolute `executable`, string-array
`arguments`, absolute `cwd`, `environment` object containing only deliberate
process-local changes, `timeoutSeconds` (at most 7200), and `requireCleanAfter`.
Use empty objects and arrays explicitly. Do not put credentials in a recipe or
environment delta, since both become evidence. The observer starts executables
directly with Windows argument quoting, without interpolating a shell command.
External gate scripts must also be frozen inputs. Paths below are operator-set
variables, not default release destinations:

```powershell
. ./scripts/profile-windows-gui-build.ps1
Invoke-WindowsGuiBuildProfile -Repository $cleanCheckout -Vault $vaultRoot `
    -RecipePath $releasedRecipe -ExpectedRecipeSha256 $releasedRecipeHash `
    -EvidencePath $newExternalEvidence
```

Retain the existing release owners and this order in the released recipe:

1. Verify portable Node 26.8.1 and bundled npm 11.19.0, including the child's
   `process.execPath`. Use their absolute executables and process-only PATH.
   Run `npm ci` against the exact lock. Preserve warnings and executed lifecycle
   script identities; a new identity or runtime mismatch stops dependent stages.
2. Check clean source, then `verify:build-scripts`, forced
   `build:modular-binaries:win:x64 -- --force`, and `build:collect-logs:win:x64`.
   Freeze the complete output manifests and hashes. Read Go build information
   statically with `go version -m`, requiring the released VCS revision and
   `vcs.modified=false`. Never execute a product binary to inspect it.
3. Run `generate:icons`, then an exact tracked-source check; run `licenses`, then
   another exact check. Set `requireCleanAfter=true` on these recipe steps. A
   generator mismatch requires a committed-source correction, not normalization
   of the frozen checkout. Verify the pinned checked-in Kaizen CSS.
4. Run the existing `electron-vite build` directly. Do not substitute `npm build`
   with its live CSS prehook or Windows convenience scripts selecting NSIS.
   Stage only the signed VC prerequisite through its existing owner. Freeze the
   production dependency files before packaging, including hashes and namespaces.
5. Use the existing electron-builder owner with
   `--win --x64 --dir --publish never` and an explicit private external output.
   Do not run NSIS, Squirrel, the installer, PAIR or its services. Reconcile the
   final clean source, complete folder/ASAR inventories, packaged Go hashes,
   notices and dependency bytes against the pre-package freeze. Explain every
   output difference; a failed gate stops the chain without automatic retry.

The observer verifies clean exact source before starting and checks portable
Node/npm identity before each step. It records the source index fingerprint,
lock and recipe hashes, argv/cwd/environment delta, UTC and monotonic duration,
exit status, raw stream hashes and process observations. Canonical manifest,
dependency, signature and byte-chain checks remain explicit release gate steps,
not conclusions inferred from a successful child exit. No build or performance
measurement is supplied by installing this observer.

Each raw stdout/stderr stream is limited to 16 MiB. Overflow, a deadline, a
capture failure or a nonzero exit retains diagnostics and stops dependent steps.
Process sampling targets 250 ms and uses PID plus creation time, not PID alone.
Children start suspended inside a kill-on-close Windows job before their first
instruction. A surviving descendant fails the stage and is terminated through
that job, independently of whether sampling observed its parent. Deliberate
stage PATH values are preserved after the portable Node prefix, and toolchain
probes receive the same effective environment. Reserved evidence names are
rejected before any recipe stage starts. Recipes and toolchain text are decoded
as UTF-8.
Private bytes and working set peaks are sampled lower bounds; working sets can
share physical pages. Missed short-lived processes, missing metrics, network/IO
wait and sampling gaps remain unknown. Retain the gap and observer-overhead
records. Reconstruct observed parent/creation edges and stage ordering from
receipts; distinguish serial stage sum from wall duration, sampling overhead and
human/coordinator gaps. Do not call a duration ranking a proven critical path or
claim a speedup without comparable released before/after evidence. Split a costly
composite at its existing owner only after its operation frequency, unit cost,
cache/download behavior and unexplained residual have been established.
CPU interval deltas retain creation identities, including competing processes;
a first observation has unknown interval usage. CPU percentages use one core as
100 percent. Host-process CPU deltas include the stream pumps and may include
other work in that host. Toolchain probe time is recorded separately. Sample,
identity and observation-count bounds also stop dependent work, rather than
silently discarding evidence. Treat any such stopped run as diagnostic.
A process-metric query failure, including permission denial, also stops the
dependent chain while retaining the gap and failure receipts. A missing process
observation invalidates its CPU baseline; a later appearance has unknown interval
usage rather than a percentage calculated over the wrong window.

## Cleaning Up a Build from Source

A source build has nothing to uninstall — deleting the checkout removes the
application. What it leaves behind is the same per-user data any install creates,
so reset that the same way. Alongside the in-app
**Settings > Service > Reset app data**, a script does the same job without the
application running:

```bash
./scripts/wipe-app-data.sh --dry-run    # list what would be deleted
./scripts/wipe-app-data.sh --confirm    # delete it
```

On Windows use `scripts\wipe-app-data.cmd` with the same flags. Neither script
needs Node, and both exclude engine model libraries such as `~/.ollama` and
`~/.lmstudio` by design, so a reset does not cost you re-downloading models.
Start with `--dry-run`; it prints the exact paths and deletes nothing.

If the machine belongs to a cluster, leave the cluster as well, or the other
nodes keep listing it as a member. Refer to
[Uninstalling](../README.md#uninstalling).
