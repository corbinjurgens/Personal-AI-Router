# Local qualification and freshness

A hybrid request may run on a local model only within bounds that were measured
for that exact model, engine launch and chat template. This page describes the
qualification evidence a node holds, how each strict request is checked against
it, and the identity that keeps that evidence current. It builds on
[Strict local admission](strict-local-admission.mdx).

The unified HTTP listener uses the common inference lifecycle and qualified
local/peer selection; engine facades retain their own alias-refusal rules.
Provider API egress remains disabled by build availability and policy permission
gates, so API-only aliases cannot fall back to local candidates. Qualification
does not activate those paths or establish real-host acceptance. No qualification
evidence ships with PAIR; operator-created evidence may exist and must satisfy
the current contract. The synthetic fixtures in
`services/nvpair-proxy/testdata/local-qualification.json` and
`services/nvpair-proxy/testdata/opencode-shapes.json` qualify nothing real.

## Qualification evidence

Each node reads `local-qualification.json` from the per-user application data
directory (the same directory as `node-policy.json`) once when its proxy starts.
A missing file means no model is qualified. A file that cannot be read or that
fails validation is ignored as a whole and logged; nothing is qualified from it.

```json
{
  "version": 2,
  "qualifications": [{
    "id": "synthetic-example",
    "revision": "1",
    "engine": "ollama",
    "model": "example:8b",
    "modelDigests": ["1111111111111111111111111111111111111111111111111111111111111111"],
    "launchDigests": ["2222222222222222222222222222222222222222222222222222222222222222"],
    "requestOptions": {"temperature": 0},
    "tokenizer": "example-byte-level-bpe",
    "chatTemplate": "example-template@sha256-prefix",
    "contextTokens": 8192,
    "maxOutputTokens": 2048,
    "routes": ["/v1/chat/completions"],
    "shapes": {
      "tools": true,
      "structuredOutput": ["json_object", "json_schema"],
      "reasoningReplay": false
    },
    "accounting": {
      "method": "utf8-bytes",
      "requestOverheadTokens": 16,
      "messageOverheadTokens": 8,
      "toolOverheadTokens": 32,
      "schemaOverheadTokens": 32
    },
    "evidence": "Synthetic example only; these digests and bounds qualify no real model, launch, tokenizer or template."
  }]
}
```

| Field | Meaning |
| --- | --- |
| `version` | Document schema integer `2`; older evidence is not migrated automatically. |
| `id`, `revision` | Identity of this qualification. A profile names exactly one id and revision. |
| `engine`, `model` | The engine and model; the model is compared after the engine's naming normalization. |
| `modelDigests` | Content identities of the model the bounds hold for. Ollama uses its `/api/tags` digest; NE uses the aggregate artifact manifest digest described below. |
| `launchDigests` | Launches the bounds hold for (Identity, below). |
| `requestOptions` | The profile defaults the bounds were measured with. The profile's `requestOptions` must be equal. |
| `requestOptionsMode` | The request precedence the evidence covers: `defaults` when omitted, or `enforced`. The profile's effective mode must match. |
| `tokenizer`, `chatTemplate` | Names of the tokenizer and template the accounting was verified against. |
| `contextTokens` | The served context the bounds hold for, at most 16777216. Each overhead is below it. |
| `maxOutputTokens` | The largest output a request may ask for; below `contextTokens`. |
| `routes` | Request shapes covered. Only `/v1/chat/completions` is supported. |
| `shapes.tools` | Required non-null boolean covering function definitions, requiring choices and tool history. `false` grants none of them. |
| `shapes.structuredOutput` | Required non-null array of distinct `json_object` and/or `json_schema` names. Each mode requires its own evidence; `[]` grants neither. |
| `shapes.reasoningReplay` | Required non-null boolean; currently must be `false`. `true` is refused while replay is unsupported. |
| `accounting` | How input tokens are bounded (below). |
| `evidence` | Nonsecret provenance of the measurement. |

Unknown fields, repeated JSON keys, missing/null/partial shape declarations,
wrong shape types, unknown or repeated JSON modes, an unsupported version,
method or route, or a repeated id and revision reject the whole document.
Version-1 evidence is rejected, with no compatibility fallback. Requalify
explicitly against the current content, launch, defaults, tokenizer and template,
record the measured shapes and bounds under schema `2`, and update the profile's
qualification reference when its revision changes. Merely changing the version
integer is not requalification. This applies to existing operator evidence too;
the shipped fixtures establish no fleet-wide absence of evidence.

### Accounting

The only method is `utf8-bytes`. It bounds input tokens by the UTF-8 bytes of
everything the template renders, which holds for a byte-level BPE tokenizer: each
token covers at least one byte. The template's own tokens are covered by the
declared overheads. For one request the input bound is the request overhead, plus
for each message its overhead and the bytes of its role, name, tool call id and
text content and the compact JSON of each of its tool calls, plus for each tool
definition its overhead and the bytes of its compact JSON, plus the UTF-8 bytes
of a string `tool_choice` or the compact JSON bytes of an object choice,
plus, for a structured response, the schema overhead and the bytes of its name,
description and compact schema. A qualification is valid only when its evidence
shows the tokenizer is byte-level and the overheads cover the template's rendering
of every allowed shape, including tools and schemas. An estimate such as bytes
divided by four is never used.

Empty `tools:[]` contributes zero definition overhead. `json_object` adds the
schema overhead; `json_schema` also adds its name, description and compact schema
bytes. Streaming/usage metadata adds no input charge. In the synthetic
`empty-tools` fixture, request/message overheads are 8/4 and `user`/`hi` contribute
4/2 bytes: `8 + 4 + 4 + 2 = 18`, with output 16 supplied by matching defaults.
The `overlay-json-object` and `overlay-json-schema` fixtures independently bound
those modes at 34 and 52 input tokens with those fixtures' schema overhead 16.
These are fixture arithmetic, not measured overheads for the example above or a
real template. Replay is refused and has no accepted input accounting today.

## Profiles

A model opts in through its profile in the node policy:

```json
{"name": "example", "engine": "ollama", "model": "example:8b",
 "contextTokens": 8192, "maxOutputTokens": 2048, "maxConcurrent": 1,
 "qualification": {"id": "synthetic-example", "revision": "1"},
 "requestOptions": {"temperature": 0}}
```

A profile with a qualification needs nonzero `contextTokens` and
`maxOutputTokens`, with the output ceiling below the context. The node's
advertisement copies `maxOutputTokens` and `qualification` onto each declared role
served by that profile. A router offers a role for a hybrid request only when the
role carries a valid qualification reference, a served context and an output
ceiling below it, and the node advertises a valid strict entry for the role's
model. These advertised values are hints; the destination checks every request
itself.

## Installing strict capacity

`requestOptionsMode` is `defaults` when omitted, and explicit `defaults`
normalizes to omission. Qualification requires equal options and equal effective
mode in profile and evidence. Defaults-mode requests allow client overrides;
enforced-mode requests replace configured leaves recursively before strict
validation. This path retains strict key/shape checks and
refuses configured-key ambiguity with a fixed HTTP `400` message. Unconfigured fields
remain request-controlled within existing strict admission bounds.
Omitted qualification mode also means `defaults`. Changing the profile's mode
without matching qualification evidence invalidates installed strict capacity.
The local strict grammar additionally accepts integer `top_k >= 0` and finite
numeric `min_p` and `repeat_penalty`; the public Chat grammar is unchanged.

The separate `localOnly` flag is already a target-owned policy-edit lock. It
does not supply qualification, force a request value or install capacity.
See the [broker contract](../services/nvpair-ui-broker/README.md#model-inference-settings-and-target-owned-locks)
for administrative rules and the shared-draft desktop editor. Typed numeric
fields target llama.cpp and LM Studio, with typed `min_p` only for llama.cpp.
Advanced policy JSON preserves uncommon and Ollama-native settings but does
not establish engine-specific sampler acceptance. An engine-rejected enforced
value can make every request fail until corrected. Model-card values are
per-model starting points, not product defaults or qualification evidence.

The proxy derives its strict capability whenever the policy or the engine identity
changes, and reports it to the broker. A profile's model is installed only when
all of the following hold:

- the evidence holds the profile's qualification id and revision, for the same
  engine and normalized model;
- the engine has an identity, its launch digest is in `launchDigests` and the
  model's content digest is in `modelDigests`;
- the profile's `requestOptions` and effective `requestOptionsMode` equal the
  qualified ones, and its `contextTokens`
  and `maxOutputTokens` do not exceed the qualified ones;
- the model's effective concurrency is finite.

Capability coverage also fails closed: a profile advertising `tools` requires
`shapes.tools:true`; `structured` requires both JSON modes because that capability
has no per-mode granularity. A profile declaring only one JSON mode may serve it
without advertising the broad `structured` capability. Empty capabilities add no
shape requirement. Vision, embeddings and unknown capabilities do not install
through this text-only contract; missing coverage does not silently downgrade a
profile.

When the current identity includes a `serving` map, the normalized model must
also have a valid envelope bound to that content digest. Missing envelopes,
conflicting normalized aliases and absent or null memory domains refuse strict
capacity. The qualification's `contextTokens` and `maxOutputTokens` must fit
the envelope's per-slot context and output ceilings, the effective policy or
profile concurrency must not exceed its slots, and the profile's `memoryBytes`
must be at least the explicitly declared `vramBytes`. Equality is accepted.
Host RAM remains a separate declared domain; it is not added to VRAM for this
comparison. A nil `serving` map retains the existing non-NE qualification and
digest rules, including Ollama's inventory digests.

The installed entry carries the identity `{engineRunId, settingsFingerprint,
modelDigest}` that a strict request must name. When any input changes, the entry
is withdrawn or replaced, and tickets admitted under the previous entry can no
longer dispatch. Envelope-only replacements also advance the existing admission
generation, even if the outward strict entry is unchanged. Requests validated
before replacement and tickets awaiting dispatch must be validated and admitted
again; withdrawal followed by reconnect does not restore their old generation.

## Validating a strict request

Before any wake, unload, slot or inference, the destination:

1. requires the model to be installed under exactly the identity the request
   names (otherwise 503 `strict-admission`);
2. checks incoming keys and applies the profile's `requestOptions` under its
   effective mode (defaults fill absent fields; enforced configured leaves
   replace request values), then checks every effective top-level key again,
   including option-injected keys;
3. rejects (400 `strict-qualification`) unsupported fields/shapes, repeated or
   case-variant top-level keys, images or other non-text parts, and request-level
   context overrides. `reasoning_effort` and `parallel_tool_calls` are refused
   whenever present, including `null`, `false` and defaults-injected values;
4. requires one finite output bound (`max_tokens` or `max_completion_tokens`,
   equal when both are sent), no larger than the profile's and the
   qualification's output ceilings;
5. requires the input bound plus the output bound to fit the smaller of the
   profile's and qualification's contexts, then forwards the validated effective
   body unchanged except for the explicit `store:false` removal below.

Policy denials name fields and bounds, never request content. Nested malformed
members can retain generic diagnostics such as `unsupported shape`; there is no
promise of a specialized shape-policy error for every decode failure. Existing
text, sampling, streaming and output/default behavior remains subject to its
existing validation; this shape contract is not a general scalar/null tightening.

### Tools, JSON modes and replay

Present `tools` must be a non-null array. Omission and `tools:[]` mean no active
definitions and do not by themselves require tools evidence. An absent choice,
`none` or `auto` permits omitted/empty definitions; `required` and a named function
choice require both tools evidence and nonempty definitions. Function
`parameters` is optional, but must be an object when supplied. Nonempty
definitions, assistant `tool_calls` and tool-role history require `shapes.tools`.
Qualified history needs no active definitions in that request. Assistant null
content still requires nonempty tool calls; calls belong only to an assistant
and `tool_call_id` only to a tool message. Null tool arrays, calls, choices and
supplied parameters, malformed members and new shapes are refused.

For example, this synthetic history-only request needs tools evidence despite
having zero active-definition overhead:

```json
{"model":"fixture-model","messages":[{"role":"assistant","content":null,"tool_calls":[{"id":"c1","type":"function","function":{"name":"f","arguments":"{}"}}]},{"role":"tool","tool_call_id":"c1","content":"ok"}],"tools":[],"max_completion_tokens":16}
```

`response_format` omission or `{"type":"text"}` needs no JSON-mode evidence.
`{"type":"json_object"}` requires exactly `json_object` coverage;
`{"type":"json_schema","json_schema":{"name":"f","schema":{"type":"object"}}}`
requires exactly `json_schema` coverage. Neither grants the other. Null, malformed
or unsupported formats are refused.

Schema `2` requires `reasoningReplay:false` and refuses `true`. Inbound
`reasoning_content` is currently refused on every role, including assistant
empty strings, nonempty strings and null. It is not stripped to make a request
pass. Supporting replay would require a separately approved assistant-only,
exact content/launch/template and reasoning-format qualification, unchanged
forwarding, and UTF-8 byte accounting (empty string zero bytes) plus existing
message/template overheads. That is a future qualification boundary, not current
acceptance. Unqualified local reasoning models remain incompatible with replaying
turns; exact-template evidence alone cannot enable an unsupported implementation.

### Pinned OpenCode compatibility

The accepted inventories recorded OpenCode CLI 2.0.32 at native release source
`843a6c514e606b436a7fe713422ace0a93ad3d61` and 2.1.1 at
`ba546ec1598a70db2570e9c6258028d955ba8f58`, using the native
`@opencode/ai/providers/openai-compatible` path. These historical versions are
not a statement about an installed 2.1.4 or the current effective configuration.
The source-lock SDK devDependency is not the operative converter.

PAIR accepts `store:false` as a no-op, removes it before forwarding, and applies no accounting charge; `store:true` is explicitly refused because PAIR does not store requests. Omitting `store` preserves existing behavior.

Only JSON boolean false is accepted, on both incoming and merged bodies; null
and every other type are refused. Normal defaults precedence applies before
removal. OpenCode 2.0.32's pinned generic-provider
[store detection](https://github.com/anomalyco/opencode/blob/843a6c514e606b436a7fe713422ace0a93ad3d61/packages/ai/src/protocols/openai-chat.ts#L717-L757)
and [lowering](https://github.com/anomalyco/opencode/blob/843a6c514e606b436a7fe713422ace0a93ad3d61/packages/ai/src/protocols/openai-chat.ts#L787-L803)
emit `store:false` by default. `compatibility.supportsStore:false` suppresses that
emission as a pre-fix workaround; it is not required after PAIR's Task 7 fix.
This local no-op does not extend the separate public-account adapter's fields.

Both inventoried native releases automatically replay present unstructured
reasoning as assistant `reasoning_content`, even with `requireReasoning:false`:
[2.0.32 lowering](https://github.com/anomalyco/opencode/blob/843a6c514e606b436a7fe713422ace0a93ad3d61/packages/ai/src/protocols/openai-chat.ts#L412-L665),
[2.1.1 lowering](https://github.com/anomalyco/opencode/blob/ba546ec1598a70db2570e9c6258028d955ba8f58/packages/ai/src/protocols/openai-chat.ts#L436-L498).
There is no established client replay-off switch. Native
[history lowering](https://github.com/anomalyco/opencode/blob/ba546ec1598a70db2570e9c6258028d955ba8f58/packages/ai/src/protocols/openai-chat.ts#L667-L807)
also emits `tools:[]` for history without active definitions. Generic completion
maxima and streaming usage depend on the selected provider/call and compatibility
settings; an omitted maximum needs a qualified profile default. JSON-mode and
snake-case parallel examples in the fixtures are raw-overlay regression cases,
not claims of default native emission. Effort/parallel remain refused.

These immutable source claims and retained extracted-converter fixtures establish
construction only. Binary/source equivalence, effective runtime hooks/config,
installed wire traffic, full provider HTTP/SSE execution and real local-template
qualification remain unverified by this evidence. The synthetic
`native-streaming-usage` path can forward reasoning response data, but its next
assistant replay is refused; it does not prove working real-model multi-turn
reasoning.

## Identity and freshness

The identity binds a qualification to what is actually running:

| Part | Producer | Changes when |
| --- | --- | --- |
| `engineRunId` | engine-manager | the engine is started or adopted, or engine-manager restarts |
| launch digest | engine-manager | the executable, argv or explicit environment changes; NE also binds the approved prepared launch inputs |
| model content digest | engine-manager | the model's content changes, including a same-name replacement |
| `settingsFingerprint` | broker | a settings revision is applied, or the broker restarts |

engine-manager reports identity only for engines it launched itself as an owned
process. An adopted service or a command-mode daemon was not started from a launch
it can name, so it has no identity and stays ineligible. The launch digest is the
SHA-256 of a JSON document holding the executable path, size and modification
time, the argument list and the sorted explicit environment assignments;
engine-manager logs it as `launch_digest` whenever an engine's identity changes,
which is how a qualifying operator records it. The inherited environment of the
service is not part of it.

For engines without an NE serving declaration, model content digests come from the engine's own inventory when its manifest's
`list_models` result declares a `digest` field (Ollama does). Other engines report
none, so their models are not installed. Engines that declare one are listed on
every watcher tick, and each digest is reported only with the run it was listed
under. An approved NE owned launch instead derives content from its declared
artifact manifest, as described below; inventory cannot replace that identity.

engine-manager sends the broker `engine:model-identity`, a whole snapshot
`{engines: {<engine>: {engineRunId, launchDigest, modelDigests, serving?}}}`, after its first
sweep and whenever it changes; every start, stop or adoption triggers a sweep. The
broker joins it with the SHA-256 fingerprint of each engine's applied settings
revision and pushes `node/set-model-identity` to the proxy; it also drops an
engine at once when it stops, drops all of them when engine-manager exits, and
withholds from its advertisement any reported model whose identity is no longer
the current one.

### NE artifact attestation

For each consumed model, shard and draft artifact, obtain a trusted full-file
SHA-256 from pinned HF LFS metadata where available. Record the pinned repository
revision and metadata reference with `hf-lfs-sha256` provenance. A SHA-shaped
blob filename alone is not verification. Otherwise run an external one-time
`shasum -a 256 /absolute/path/to/artifact` and record `one-time-sha256`
provenance and its receipt. PAIR does not perform this full model hash.
Keep original locations and HF snapshot symlinks; no copy/import is required.

Submit those digests in `serving.models[].artifacts` in native consumption/shard
order through the existing authorized E settings preview/apply route. Review
the returned bindings (source, resolved regular target, size, nanosecond mtime,
first/last 64 KiB sample) and native-source digest before applying that exact
preview. A shorter-than-128-KiB file is sampled once. Changed bindings require
explicit renewed verification and apply; PAIR never silently re-attests bytes.

The envelope's `contentDigest` is an aggregate manifest digest, not a GGUF's
individual SHA-256. It hashes canonical JSON with version
`pair-serving-content-v1` and ordered artifact entries of `role`, `sizeBytes`
and lowercase `sha256`, excluding paths, timestamps, samples and operator
labels. Renewed bindings after relocation preserve content identity. NE's
`launchDigest` hashes a `pair-serving-launch-v1` document containing the existing
pre-snapshot executable-stat/argv/environment digest and the approved prepared
digest. It includes source/declaration/envelope/placement/retention/capacity
changes but excludes random snapshot generation directories.

After an owned validated launch, copy `serving[exactModelId].contentDigest`
from `engine:model-identity` (also `launchValidated[].contentDigest` in authorized
settings readback) into the existing B record's `modelDigests`. Copy the reported
`launchDigest` (or its public `launch_digest` log value) into `launchDigests`.
Record digest provenance and the exact runtime/envelope in qualification
`evidence`; no new B provenance acceptance field or schema is added. This
identity alone qualifies nothing: measurement and the existing B checks remain
required. Cold configured envelopes are not measured effective runtime limits;
declared memory is not an OS allocation limiter.

Full inventory reconciliation and action pokes recheck bindings/native inputs
without full model hashing. Drift publishes an empty model digest map, omits
`serving`, and latches settings `mismatch` until successful explicit apply/start.
The cheap binding cannot detect a deliberate middle-only change preserving
size, mtime and both sampled regions. Trusted full-file assertions and operator
control of the source remain part of this contract.

For the pinned llama build, retention `"-1"` disables idle expiry; positive
seconds remain valid and zero or values below -1 reject. SR 5b owns retention
enforcement and router-capacity comparison with its revision-bound resident
set. Plain direct-model output enforcement remains deferred until after I 4b;
router-cached undeclared models and native output defaults retain their current
behavior on that path. Strict readiness checks the current launch-validated
envelope against qualification and profile bounds; it does not require a loaded
observation or load a cold model to establish eligibility. Cold validation proves
the prepared configuration and bindings, not observed runtime allocation.
Declared RAM/VRAM bounds are operator-approved conservative admission values,
not measured usage or OS-enforced RSS/VRAM limits. Loaded observations and actual
host qualification remain separate acceptance gates. Further Strata-specific
work is deferred.

Invalidation happens before the change it guards wherever PAIR makes the change:

| Event | Effect |
| --- | --- |
| A settings operation (apply or recovery) | The broker withdraws the engine's settings identity and waits for the proxy to acknowledge it before `engine:configure-launch` runs; if that cannot be confirmed the operation fails before the engine is touched. A new applied revision has a new fingerprint. |
| A PAIR model mutation (manifest-bound delete/pull, streaming pull or destination copy, including typed delete and `ec` callers) | Like settings, the mutation waits for confirmed destination withdrawal before changing content. The whole engine's model identity is withdrawn; it returns only from fresh post-completion inventory, including after failure. |
| Lower context, changed template flag, other launch arguments or an engine upgrade | New launch digest; not covered by the evidence, so not installed. |
| Engine restart or adoption | New run id; requests naming the old one are refused. |
| Same-name model replacement or a changed template layer | New content digest; not installed until evidence names it. |
| Profile bounds above the evidence, other defaults, or a stale qualification revision | Not installed. |
| Stale origin metadata | The destination revalidates identity and body. |

Withdrawal rejects cached strict envelopes and tickets that have not passed
their final dispatch check; it does not cancel already dispatched inference.
The remaining polling window is for models changed outside PAIR: artifact/source
binding validation runs on full-inventory sweeps, scheduled every 60 seconds and
also triggered by an action poke, rather than at dispatch. The watcher's ordinary
loaded-model ticks do not each perform this validation.

## Daily adapter and residency contract

`servedModels` permits on-demand admission; `residentModels` is the desired
always-loaded subset, not an inventory report or evidence of allocation. Saving
either list does not qualify a model. Automatic residency requires the existing
B qualification and current owned NE serving identity, a unique normalized
profile, finite context, output and concurrency, and approved memory bounds.
Profile context must equal native per-slot allocation; qualification must cover
that allocation and its output ceiling, and effective concurrency must equal
native slots. A model-only load cannot shrink native allocation.

Daily adapters require an explicit, non-mutating load contract: `POST` with exactly
`{model}`, and a side-effect-free loaded-model `GET` with extraction and a loaded
filter. There is no prompt, implicit load, pull, install, restart, eviction or
arbitrary-action fallback. An engine family name alone does not establish support.
Native retention must be exactly `"-1"`, disabling idle expiry, and router
capacity must fit the revision-bound resident set for that engine. The validated
`keepAliveSeconds` request value is not sent to the engine; native launch settings
own retention. Positive native expiry remains valid for other launch uses but
does not satisfy automatic residency.

The destination proxy owns admission and reserves against the whole desired set
and existing resident/in-flight memory. The broker coordinates prepare, manager
reconcile, final proxy dispatch grant, finish and authoritative observation.
Either-origin pause and durable engine lock fence automatic residency with
`paused` and `engine-locked` reasons. Ordinary saved Off of any origin reports
`engine-off`; reconciliation still requires saved On and a running engine and
does not start one. A granted peer may explicitly start or switch to an unlocked
engine despite saved Off, and may load a running one. Explicit load never starts
an Off engine. Local Stop can still cancel work already accepted for that engine.
Lock/unlock is local-only; unlocking leaves Off. Pause fences all peer management
writes, including Resume, while reads stay available. Local activation also
requires local Resume. These fences apply after acceptance as well as admission.
PG's existing route-policy owner continues to decide routes; residency does not
select a route, broaden served permission or enable hybrid dispatch.

A definite terminal manager load failure reports `unknown` with the bounded
reason `load-failed`, including finish/recovery and retained-hold readbacks.
Loaded observation is independent: a failure without inventory evidence does
not prove the model absent or capacity free. Unknown completion or transport
uncertainty continues to report `operation-timeout`; raw engine errors are not
public reasons. A transient proxy `engine-off` refusal stays `pending` without
a reason when the current manager source reports the engine running. Status
classification does not alter existing retry deadlines, hold cleanup or expiry.

Unknown loaded observations and failed or interrupted loads remain uncertainty,
not satisfaction or free capacity. Source/run/revision changes fence stale replies;
restart does not replay a persistent load queue. Fresh manager-owned loaded
allocation evidence, rather than a cold declaration or model name alone, is
required to confirm satisfaction after replacement. Resident bookkeeping is
separate from durable strict-inference quarantine: an HTTP terminal frame or
elapsed timeout does not prove inference termination.

If a manager stops mid-load without a terminal reply, its nonterminal resident
hold remains `unknown`/`operation-timeout` until the next policy edit or a proxy
restart; time passing or manager replacement does not clear it. After proxy or
manager replacement, fresh inventory and the observed serving envelope from the
current manager can report the resident `satisfied` while the hold remains.
Engines adopted from an earlier manager run stay `unknown` because they lack
confirmable manager-owned allocation evidence.

Real-host acceptance remains pending: approved launch/binding evidence,
tokenizer/template measurement, loaded context and slots, retention behavior,
router capacity, local veto races and restart recovery must be demonstrated on
the selected host and engine build. Configured bounds and synthetic tests do not
establish Windows/GPU behavior or actual RAM/VRAM usage. Strata has no loaded
allocation observation producer; its declaration alone cannot prove residency.

## Not covered here

- Actual qualification evidence. It must come from the target machine: the model
  and engine version, measured tokenizer behavior and template overheads covering
  every allowed shape, the served context, and the launch and content digests.
- Termination evidence. Strict work still counts as uncertain after it finishes
  until reconciliation proves the engine stopped generating; releasing that
  capacity belongs to hybrid dispatch together with actual engine evidence.
- The hybrid dispatch lifecycle beyond qualification, including its permission,
  cancellation and real-host acceptance gates; see
  [Hybrid routing](hybrid-routing.mdx).
