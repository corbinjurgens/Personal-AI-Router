# Configure model settings

Open **Configure** on a model row in Model Manager, or **Configure model** in
Routing settings. The side panel shows the node, engine and exact native model
identifier. Configuration is available while the engine is Off. A known row
does not prove its model files are complete; Routing also accepts an exact
model identifier when live inventory is unavailable.

For llama.cpp, create a profile with a unique profile key, then edit the
supported generation fields. Blank fields inherit the engine's behavior.
Resetting a field removes its override. **Defaults** allows request values to
override the configured defaults; **Enforced** replaces the configured keys in
subsequent requests. Other options remain in Advanced policy JSON.

Saving generation preferences does not start an engine, load or download a
model, or change native context allocation or GPU placement. It affects
subsequent requests on the serving node. An Off engine stays Off.

## Profiles

A profile names its engine, and its key identifies a node-local saved
configuration. For typed llama.cpp loads it also identifies the preset section
and served id; the native model
identifier selects the artifacts. The display name and icon are presentation
metadata, independent of that key. Several profiles can use the same model
artifacts with different launch and request settings.

Choose **New profile**, enter its key, display name and icon, then review and
apply the change. The suggested key is a lowercase model slug; edit it as needed.
New profiles inherit the target engine's load defaults until you select overrides.
Keys must be unique on the node: nonempty valid UTF-8, at most 512 bytes, without
control characters. A key cannot equal a declared role, and every colon name
whose prefix is a valid role name is reserved, including `coder:api`,
`coder:local` and unrecognized suffixes such as `coder:fast`. This reservation
does not apply to native model identifiers, provider model identifiers or
artifact identifiers. `coder-api` and `coder-local` are valid keys. Select an
existing profile by its display name, key and context to edit its own settings.

Profile context is derived from the resolved launch settings' per-slot context,
not independently entered as a policy bound. Total native context and slots
remain distinct. Native fit still requires realized native context evidence;
requested context alone does not establish it. Creating or deploying a profile
does not qualify its model.

Each declared role holds an ordered list of this node's profile keys. In node
settings, add or remove memberships and move entries up or down before saving
the revision-checked policy. Deploy selects only existing target roles and never
creates a role. Node cards show model repository and quantization tags by
default, with Unknown for unavailable identity. **Show profile summaries** adds
the icon, display name and differentiating settings for the session. Clicking
an entry opens settings at that profile.

### Roles

Create, rename, remove and reorder roles only in the **Roles** section of node
settings. Names match `[a-z0-9][a-z0-9._-]{0,63}` (at most 64 bytes). Nodes start
with no roles. Roles have no built-in names or defaults and belong to each node rather than
a cluster-wide store. An empty role can be saved before assigning profiles.
Order them weakest first: Allow stronger tries roles further down the requesting
node's list; Allow weaker tries roles further up. Deploy and model settings
select existing target roles and never create them.

When editing this PC, renaming also moves its API configuration in the same save,
and removing deletes it. API configuration means a nonempty `tiers[name]` list
or the presence of `routing.tiers[name]`; an empty `tiers` list alone is absent.
If both old and new names hold configuration, even in different maps, rename is
refused atomically, names both sides and asks for another name. Nothing is
overwritten or combined. If only one name holds configuration, it ends under
the new name, retaining destination-only settings when the old name has none.
Every old-name key is removed, including empty ones.

Remote role edits leave that node's private API entries unseen and unchanged.
Every remote rename and removal confirmation says that API entries on the named
node can't be seen from here and stay as they are. No private configuration
rename or removal is sent or inferred. API entries under an undeclared old name
remain stored and unused. Role edits do not coordinate a cluster-wide change.

Any role may have API entries and colon overrides, but public API dispatch is
disabled in this build. Its `:api` alias is listed and refused; enabled
deployments and remote or paid permissions cannot be saved. See
[Hybrid routing](hybrid-routing.mdx) for selection and availability limits.

### Hand-written preset conversion

For a llama.cpp engine with an external hand-written preset and no typed loads,
the first saved typed model change, including deploy, converts the whole preset.
There is no separate Import action. The successful preview says **Saving
converts this engine's hand-written preset into** a count of **profiles**, using
the actual converted loads returned by that preview.

Every section becomes a keyed profile with derived per-slot context and artifact
identity. A new profile uses its original section name as its key and display
name. Existing profiles retain their display name, icon, request options and
other user-owned settings while their derived context and identity are updated.
Conversion itself creates no roles and preserves role lists. An explicit role
membership patch still applies to the selected profile. An unresolved section
refuses the whole conversion; review and apply remain required. Native fit and
extra options retain their validation and unpriced limitations below.

## Native load settings and inspection

The same panel separates native load preferences from Generation settings and
Routing/residency. Choose **Configure load and routing settings** to inspect
those controls. For llama.cpp, Basic load covers tokens per request, slots,
GPU placement and separate K/V cache precision. Advanced controls expose only
the support, ranges and inherited sources reported by the target service.
Clearing an override means inheritance, not an invented default. Total context
allocation is separate from tokens per request and policy admission limits.

Inspection is a read. Artifact status, source and binding assurance describe
what the target actually resolved. Unavailable facts or estimates remain
Unknown; they do not become zero or evidence of a complete model. Unsupported
controls retain their reported reason. No inspection loads, downloads or starts
a model, and this editor does not create qualification.
The advisory contract can identify an engine report or a PAIR estimate and name
costs that were not priced. A provider verdict is separate from PAIR's memory
comparison, and a partial report does not imply complete accounting. No engine
report provider is enabled by this contract alone.
Main, draft and companion files are labelled separately. A companion such as a
projector is not presented as another main-model shard.

For an already authorized owned llama.cpp load, inspection can also show
**Estimated versus native-reported buffers for this load**. This read-only table
uses the estimate captured for that load's artifacts, native source and effective
options, separately from your edited draft. Native sizes are rounded allocation
reports, not physical GPU usage or a complete-process peak. Missing reports,
unsupported builds, incomplete coverage and unmapped devices remain Unknown.
Recovered reports are historical; losing currentness preserves the captured
facts. Inspect never starts a load to obtain a report. See
[Native buffer observations](model-buffer-observations.mdx) for formats, privacy
and limitations. Reports never retune estimates, margins, Auto, admission or
qualification.

Memory advice uses the service's per-pool `capacityFit` and `freeFit` values:
`unknown`, `exceeds`, `tight` or `fits`. Available memory is distinct from total
capacity. Each independent pool reserves ten percent of its capacity, rounded
up, plus 512 MiB. Expected bytes above available bytes exceed the pool. A pool
fits when its upper bound plus reserve is at most the available amount;
otherwise it is tight, including equality between expected and available bytes.
UMA represents one shared pool.
Measurement source, sample identity, measurement timestamps and bounded remaining
validity accompany comparisons. The estimate timestamp describes computation,
not a new measurement. Expiry withdraws comparisons while preserving components.
The estimate block renders the target service's comparisons without recomputing
cost completeness, pool totals or reserves in the desktop. It shows expected
memory, the lower-to-upper range and the source label: **Estimate**, **Your
figure**, **Measured** or **Engine report**. Component rows retain their basis;
heuristic costs are labelled uncalibrated. Unpriced source costs appear under
**Not included in this estimate**, and each pool retains its reported Unknown
reasons. Missing provenance, ranges and reserves display Unknown rather than
invented values. Device pools retain their physical identity, and UMA appears
once without adding host or device capacities. Stale evidence removes both
capacity and free-memory verdicts, while retained amounts remain historical.

The canonical component names are `weights`, `attention-cache`,
`recurrent-state`, `compute-workspace`, `prompt-cache`, `companions` and
`runtime-overhead`. Priced rows carry canonical decimal `bytes` (expected),
`lowBytes` and `highBytes`, with `lowBytes <= bytes <= highBytes`, and a basis:
`derived`, `heuristic`, `calibrated` or `observed`. Partial rows retain the range
of their priced portion and name the unpriced residual. Unknown rows carry no
bytes. Charges crossing independent pools appear as separate component rows.
PAIR estimates sum expected and upper amounts on each pool. Partial and unknown
costs add `not priced` warnings; domainless omissions warn on every pool. Adding
uncertainty never improves a verdict. Unknown weights, expired or missing capacity
and unmapped device pools keep their comparisons Unknown.
User-stated, measured and engine-report sources instead use each domain's
`requiredBytes` and optional `requiredLowBytes` and `requiredHighBytes`, counted
once, with source-level unpriced costs shown as warnings. Component rows remain
display information for these sources. A retained engine memory plan keeps its
own provenance when a stated or measured figure is selected.
These comparisons are advisory and do not enable production Auto or admission.
Worker-only memory envelopes and frozen validation are defined
separately from public inspection and portable load edits. The target broker
injects its own self observation. Reviewed GPU allocations persist a full UUID
constraint and use `CUDA0` within that child-only visibility set; replay validates
the native libraries and environment without enumerating devices.
Manual GPU settings remain usable without a reviewed physical binding, but their
unproven GPU-domain comparisons stay Unknown. External conversion never
substitutes for an Auto review.

The service resolves available local artifacts and reads bounded metadata for
inspection. Missing, ambiguous or unavailable content remains a reported
condition. Manual finite llama.cpp load changes require a successful target
preview. Reviewed Auto remains unavailable in production; advisory component
estimates can report partial costs and Unknown comparisons. A refused
preview does not enable Apply or produce a success receipt. Profile edits use
the same coupled target preview and apply operation.

The broker retains an unaccepted review for ten minutes, within its bounded
review table. Explicit Recalculate supersedes that caller's earlier recommendation.
Apply validates the retained finite settings and never repeats the portable patch
or Auto search. An unaccepted Auto allocation must still fit fresh complete target
evidence; otherwise Recalculate is required. Accepted receipt retry and durable
recovery replay the saved result even if advisory telemetry disappears. Off,
Pause, grants, ownership and source drift remain effective. The
[estimate support contract](../services/nvpair-engine-manager/spec.md#advisory-memory-estimate-support)
describes current accounting limits; the
[option matrix](../services/nvpair-engine-manager/MANIFEST.md#typed-model-load-contract-and-option-matrix)
describes the manual native setting vocabulary, not complete-cost eligibility.

Typed manual settings currently cover finite llama.cpp allocation and the
service's supported batch, thread, KV/Flash Attention and idle/cache controls.
RoPE/YaRN extension, NUMA/RPC, tensor overrides, adapters, multimodal presets
and remaining native allocation modes require later engine-specific support. Unsupported controls
cannot be supplied as raw typed extras. Automatic qualification is outside this
workflow.

Typed llama.cpp loads also accept `fit: "on"` (unset or `"off"` keeps the
finite behavior), `fitTarget` as comma-separated MiB margins such as `"1024,512"`,
and `fitCtx` as a minimum context from 0 through 16777216. The target and minimum
require fit on. Native fit and reviewed Auto GPU placement are exclusive.
`fit` and `fitCtx` are portable; the hardware-specific `fitTarget` is not.

Extra options accept canonical raw preset keys and literal values, with at most
32 entries, keys up to 64 ASCII lowercase letters, digits or hyphens, and values
up to 1024 UTF-8 bytes. Control characters and preset comment or substitution
characters are refused. Use typed fields for typed controls; PAIR-owned artifact
and router controls and unsupported allocation controls are refused by name.
Supported table options retain native value checks. Unknown fork options remain
unknown in estimates, even when priced components would fit, and all extras
participate in configuration identity.

The extras `device`, `split-mode`, `tensor-split` and `main-gpu` select GPUs and
make placement unpriced. Inspection reports `gpu-selection`, no finite key or
memory pools, and an applied execution key for diagnostics. These loads receive
no buffer capture, stated memory or finite serving envelope. Reviewed Auto
chooses the GPU, so it refuses GPU-selection extras and sharing an engine with a
GPU-selection profile. Copy and deploy omit the descriptor's `nonPortableKeys`.

Native fit chooses placement when the model loads. These loads remain routable
and copyable, but have no finite configuration key, priced estimate verdict,
buffer capture or stated memory record. Inspection reports reason `native-fit`
and an execution key only for an applied load. The execution key binds resolved
options, artifact identities and the native build, and never substitutes for a
finite configuration key. Native `/props` `n_ctx` supplies the realized context;
the requested context and `fitCtx` do not establish it. Operator-written serving
presets retain the strict finite parser and cannot launch fit on directly.

## Review before applying load changes

A successful target preview must supply the selected-field diff, both target
revisions and a reviewed digest before Apply is available. Combined load,
generation and routing changes use one target operation; they are never two
independent saves. Editing the draft or changing target, revisions, connection,
authority, artifact identity or build identity invalidates the preview and keeps
the draft for a fresh review.
Use **Preview model changes**, then review the result before choosing
**Apply reviewed model changes**.

Runtime impact comes from the service. When it reports a whole-router restart,
the preview says **Restarts the whole llama.cpp engine**, lists affected models
and shows the existing 60-second drain bound and interruption warning. Active
requests can be interrupted when that bound expires. An omitted impact
value is Unknown, not zero, an empty model list or a promise that active work
will finish. A reported Off-preserving operation stays Off; Saved never means
Loaded.

Desired preferences, applied settings and observed runtime remain separate.
An applying or failed coupled stage retains its request identity and error.
After a lost response, status/readback checks that identity before any explicit
retry. Failed or unresolved operations require local reconciliation and a fresh
preview for explicit supersession; the editor never rolls them back, resumes a
node or silently retries them.
Native persistence can precede policy persistence. A failure at that boundary
can leave the native preset changed while policy remains unchanged. Readback
then stays applying, uneditable and unresolved, fencing ordinary policy writes
until a fresh local preview and explicit supersession reconcile it.
An operation interrupted at bare acceptance before any changes requires a fresh
local preview and explicit supersession. Progressed operations recover their
frozen target resolution; they do not recalculate preferences during restart.

The saved inference lock protects generation preferences only. Readable load
settings retain their separate permission and Pause rules. Routing and
keep-loaded changes require explicit selection and target review; residency
still needs a current finite qualified profile and target evidence.

## Drafts and saving

Routing's panel and Advanced policy JSON share one draft and the same
revision-checked Save. From Model Manager, the panel reads the selected target's
saved policy and keeps a session draft for that target. Opening a panel does not
save anything.

The panel names the draft owner. If Routing or Model Manager already owns
unsaved changes, the other editor cannot silently take them over. Use
**Discard draft and reload** only when you intend to discard those changes.
Invalid JSON remains available for correction in Advanced policy JSON.

Typed draft edits preserve unrelated source text. The desktop policy bridge
keeps policy JSON as source text for saving, readback and change notifications,
preserving every numeric spelling, including integers and decimals beyond
JavaScript number precision. The broker still validates and persists the policy.

A reconnect or newer target policy does not overwrite dirty text. A conflict
requires an explicit reload and review. Refused or uncertain saves retain the
draft; a lost reply causes readback rather than an automatic retry. Persistence
and activation are separate: a saved policy can still have activation pending
or an activation error. Remote policy readback does not report activation.

## Target permissions and generation lock

Remote changes require the target's current management permission. A paused
target refuses remote changes and must be resumed on that device.

**Only this device can edit generation settings** protects the saved profile's
generation preferences. The panel shows the saved target lock separately from
draft edits. Removing a lock in raw draft JSON cannot unlock peer controls.
Change the lock on the target itself. This protects inference settings;
native load settings remain separate.

## Profile removal and readiness

**Remove profile** requires confirmation followed by preview and apply. For a
typed load it removes the selected load, profile, role memberships, served
permission and residency for that profile key. Without a typed
load it removes the profile and role memberships and clears residency for its
native model; served permission stays in place. Model files
stay in place.

Ordinary generation setup creates no qualification. Keep-loaded residency and
strict readiness still require valid finite bounds, qualification and current
target-side evidence. A saved profile alone does not establish readiness.

After a positively reported model download completes, **Configure** is offered
without automatically opening the panel or moving keyboard focus.

## Deploy a profile to another node

Choose **Deploy to node** in the model settings panel, then select the request
and portable load fields and target devices. Initially only configured common numeric
generation fields are selected. Request precedence is a separate opt-in. A
selected field absent from the source is shown as **Clear on target** before
confirmation. Unselected target options, nested fields and mode are retained.

Each target has its own copy, target review and apply stages. Copy is skipped
automatically only when both verified main-model `contentId` values match and every draft
or companion file used by the source has a recorded SHA-256 matching a target
file of the same role. Equal main files alone do not verify a projector or draft.
When companions are unverified, the row says **Model file matches** and names
the unverified files. A match on repository, quantization and total size without
content identity says **Possibly the same file (not verified)**. In either case,
choose Copy or use the target's files; neither choice is preselected. Otherwise
the existing model-copy flow copies the files before target review. Matching
names never prove matching bytes, and deploy adds no whole-file hashing.

Deploy uses the target model identifier returned by copy or the selected local
match. If the source key is unused, deploy creates a profile. The same key for
the same model updates that profile and previews changed fields, retaining the
target display name and icon unless explicitly edited. A key belonging to a
different model requires a new profile key.
An existing descriptor-only profile can gain a typed load for the same engine
and artifact; its key becomes the served id and its other saved fields remain.
Select memberships from the target's
declared roles, shown in their order. A target with no roles shows **No roles on**
the target and asks you to create one in node settings; deployment can proceed
without role membership.

Each preview reads the target's current policy, revision and management
permission. Confirm each target separately using that revision. Conflicts,
denials, locks and disconnected targets remain separate from
other targets' results. A selected no-op still goes through the target's grant,
Pause and CAS checks. An enforced mode cannot be left with no options.
Readable source preferences can be copied even when that source is paused or
does not permit remote management; only the destination is changed.

The selected request settings and precedence, portable launch settings, profile
key, display metadata and chosen role memberships form one coupled target
change. Deploy never transfers locks, qualification, stated or measured memory,
reviewed digests, resolved loads or hardware-specific bindings. The destination
resolves its own artifacts and placement; `fitTarget` and other non-portable
descriptor keys are omitted.

### Target review and outcomes

Load fields are a separate explicit selection, restricted to portable requested
preferences. The destination resolves placement and artifacts itself. Source
resolutions, native device identifiers, paths, ports and approvals are never
copied. Selected absent overrides mean Clear on target, with the destination's
inherited source shown for review.

Role membership requires explicit target selection and review. Keep loaded
still requires the target's current finite qualified profile and evidence.

Each target uses its own inspection and reviewed operation with fresh policy
and settings revisions. Apply requires its successful preview and confirmation;
a content-copy receipt alone is not settings approval. One target's refusal or
cancellation does not stop the other targets. Rows end applied, refused with a
reason, cancelled, or unknown. A revoked management grant or revision conflict
refuses that target; **Review again** obtains a fresh review after a conflict.
Cancelling a copy uses the existing copy cancellation. Files already copied
stay on the target after later refusal or cancellation for a retry, with no
rollback.

A lost apply reply remains unknown until operation receipt and target settings
and policy-revision readback establish the result. An unresolved readback stays
unknown; matching selected fields alone does not establish an operation receipt.
There is no distributed rollback or automatic apply retry. The native-first
reconciliation fences described above still apply.

## Validation limits

Manual finite configuration and partial memory advice are implemented. Production
Auto and Fits still refuse until the complete-cost specification and
implementation are accepted. Windows process acceptance of native-buffer reporting remains
pending; source, component and UI checks are not native accuracy, physical
occupancy or calibration evidence.

Saved, activation pending and activation error are distinct outcomes. Remote
policy replies provide no activation status. A lost Save reply triggers a
readback, never an automatic resend. Equal selected fields without a correlated
operation receipt leave the outcome **unknown**. Retry requires a fresh preview
and confirmation. Content copy has
separate results: use Model Manager's existing **Copy model files** action when
needed. Deploy can include that transfer before the settings review.

Native acceptance of profile creation and deployment, copy cancellation and
retry, and whole-preset conversion remains pending on the owner machines.
Phases 06 through 08 install together after the phase 08 gate and per-node
preflight. Source and synthetic checks do not establish installed behavior,
native-fit context agreement or Windows/GPU acceptance.
