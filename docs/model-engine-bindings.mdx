# Model Engine Bindings

A node can assign a native model name to an engine in its target-local policy.
An ordinary concrete-model request, or an existing concrete-tier request, can
then wait while that node activates the assigned engine. Saving a binding starts
nothing. An absent or empty binding list leaves unbound routing behavior unchanged;
removing a binding does not proactively stop an engine.

The service path and desktop binding editor are implemented. Joined
service-process proof remains pending below. Native engine and multi-machine
acceptance is pending, not observed, for every matrix row.

## Configure the Destination Policy

The destination broker stores bindings in its existing `node-policy.json` under
policy version 2. They are device configuration, separate from the request
origin's private routing, provider accounts and tier configuration.

This JSON is a **policy fragment**, not a complete `policy:set` document. The
example assumes that the named model and engine have already been prepared:

```json
{
  "engineBindings": [
    { "engine": "ollama", "model": "qwen3:8b" }
  ]
}
```

Use the existing JSON-RPC policy APIs through the local service:

1. Read `policy:get` for the intended destination. Omit `nodeId` for this node;
   use that destination's `nodeId` for a peer.
2. Start from the returned `policy` document and edit only `engineBindings`.
   Preserve every unrelated field. A local `policy:set` defaults omitted fields,
   so submitting the fragment alone can discard unrelated configuration.
3. Send the edited document as `policy` to `policy:set`, with the same target
   and `expectedPersistedRevision` equal to the `policy.revision` read for that
   draft. On conflict, read again and deliberately reconcile the draft.
4. Read back the same target. Check the saved bindings and the reported policy
   activation state; persistence and activation are separate outcomes. After a
   lost or uncertain save response, read back before deciding what to do next.
   Do not automatically resubmit the write with a new revision.

A remote edit requires the destination's current remote-management grant;
pairing alone grants no mutation authority. Start from its peer-visible policy
document, preserve that projection, and do not add a `routing` section. The
destination preserves its protected private routing/accounts, tiers, availability
and pause provenance through the existing peer policy writer.

Clear bindings with `engineBindings: []` in that edited document. New local and
peer readbacks emit an explicit empty array. If an older target drops a requested
binding field, including an explicit clear, the relay reports model-control edits
as unsupported. A successful transport response alone is insufficient. See the
[broker policy contract](../services/nvpair-ui-broker/README.md) for the API and
recovery behavior; there is no separate binding save API or CLI subcommand.

### Native Names and Prerequisites

Use the target engine's native model name, with case preserved. Descriptor
naming controls matching: Ollama's implied `:latest` spelling can match its
tagged form; exact-name engines require their native ID. This creates no alias
between engines or between differently named models. Overlapping matching sets,
including implied-latest overlaps, are rejected even across engines. Reserved
tier aliases cannot be bound as native models.

The list permits at most 256 entries. Model identifiers must be nonempty valid
UTF-8, at most 512 bytes, without C0, DEL or C1 control characters. Each encoded
`{engine, model}` reference is additionally limited to 256 JSON bytes, including
escaping, so that smaller bound can be decisive. The current target must supply
a recognized naming descriptor. When `servedModels` is explicit, every binding
must be in that permitted set after target normalization; an explicit empty
served set permits none. See the authoritative
[binding validator](../services/shared/nodepolicy/engine_bindings.go) and
[policy model-reference bounds](../services/shared/nodepolicy/policy.go).

The engine must already be installed, fronted by a compatible enabled PAIR
facade, and runnable with its existing launch configuration. The model must be
available under that native name when the engine starts. Authentication and
engine-specific launch prerequisites still apply, including prepared llama.cpp
or Strata configuration where used. A running target missing the model refuses
without restarting it. The feature does not convert or copy models, download or
install engines or models, change presets/settings, or grant a new model-load
or qualification capability. Normal inference and admission retain their own
loading rules.

## Routing and Readiness

The proxy first applies model, protocol, serving permission, tier capability and
context constraints. Concrete OpenAI-compatible requests may inspect other
enabled compatible facades for explicit bindings. Unbound concrete names stay
on their entry engine; concrete native Ollama requests stay on their entry engine.
A binding to another engine excludes the node's conflicting old-engine model
candidate, including direct ingress. A peer ingress request is terminal: it can
prepare only that destination and cannot route onward.

Ready-first selection operates inside the existing policy ordering:

- For ordinary concrete requests, eligible inventory-backed candidates lead
  offer-only preparation candidates before scheduler/load balancing. An eligible
  explicit node selection remains authoritative and can select a cold node.
- For concrete tiers, tier/fallback rank and loaded preference still apply.
  `preferLoaded: "any"` puts loaded choices across tiers first; otherwise tier
  rank precedes warmth. Within equal rank and warmth, candidates needing no
  preparation lead preparation candidates. Eligible explicit selection can lead
  a cold preparation class within those tier/warmth constraints.
- Scheduler scores and local reservations choose inside the leading class;
  they cannot promote an unselected cold offer over an equivalent ready choice.
  Ready alternatives use zero admission wait while alternatives remain.

Here, a ready selection class is inventory evidence, not a guarantee that a
model is resident or a request will succeed. Versioned `engineBindingOffers`
are a separate advisory signal. They neither invent inventory nor prove engine
health, loaded state, model presence, qualification or strict capacity. A stopped
offered engine can retain its real proxy listener in the authenticated service
allowlist while its engine remains unhealthy. Listener reachability means the
facade can receive, refuse or prepare a request, not that the engine is ready.

After preparation, the proxy refreshes the actual engine endpoint and queries
canonical native inventory. It rechecks binding revision, peer relationship,
engine identity, availability, serving permission and candidate constraints.
Ordinary admission then rebuilds the final engine/model defaults and revalidates
after storage or queue waits and before dispatch. Receipt completion alone
does not authorize inference. Waiting for preparation holds no execution,
strict or resident ticket. Existing request-buffer and waiter bounds apply.

Strict hybrid dispatch excludes cold binding offers and dormant candidates.
Already qualified, currently ready hybrid candidates retain their existing path;
a binding cannot stand in for fresh strict identity or qualification. See the
[proxy admission specification](../services/nvpair-proxy/spec.md#122-admission).

## Activation, Replacement and Safety

Plain Off is saved state, not a prohibition: a nonempty binding permits ordinary
Off activation for its model when the other guards allow it. An engine lock
prevents activation, and unlocking leaves the engine Off. A node pause of either
origin blocks activation until **local Resume**. Pause unloads/stops engines
through its existing owner; local start/load/switch also requires Resume.

With no running conflicting engine, the manager can perform a guarded cold
start. Replacing a running engine uses the existing E4 transaction. There must
be a sole conflicting source with affirmative PAIR control and certain process
ownership. A manually started PAIR engine is not implicitly pinned. Adopted or
external sources, uncertain reclaim/stop ownership, multiple conflicting engines
and protected source residents prevent automatic displacement. There is no
multi-engine eviction policy or automatic source restoration after target failure.

Replacement withdraws the source and acknowledges drain and identity
invalidation. Before source stop, the broker requires a fresh admission snapshot
from the same proxy run proving zero active source work. Drain lasts at most
60 seconds inside the preparation budget. It does not kill old inference to
satisfy new demand, and new source work cannot extend the drain. Elapsed time,
workload counts, listener refusal or HTTP disconnect alone is not stop proof.
The manager must prove termination before target start; uncertain cleanup keeps
the operation fenced.

Local Off can preempt automatic work of either origin with a durable,
operation-scoped obligation. Delayed cleanup cannot stop newer manual work.
While automatic work or unresolved recovery reserves an engine, relevant
binding, served-set and resident-protection edits refuse busy before saving;
unrelated policy edits remain possible. Ready inference can serve a permitted
peer without management authority. Starting or replacing for a peer requires
its current target-local grant and the authenticated relationship incarnation,
rechecked at acceptance and effects. HTTP identity fields grant no authority.

### Bounds and Receipts

Automatic preparation has one absolute budget of at most **90 seconds from HTTP
entry**, clamped to the caller's remaining deadline. Candidate attempts, peer
slot acquisition, response-header waits, refresh, dwell, drain and activation
share it. A later waiter cannot extend an accepted operation's original deadline.
An accepted healthy inference stream can continue beyond the preparation window.
Manual E4 retains its separate 15-minute operation budget.

One destination preparation operation is active at a time. Demand for the same
target engine coalesces; each waiter still needs its own model and authority
readback. Competing targets refuse busy, with no cross-engine FIFO. Replacement
waits at least **60 seconds** after broker startup or any completed manual or
automatic replacement. That dwell consumes the same budget; an already-ready
target bypasses it.

Receipts and checkpoints mark automatic replacements with `automatic: true`.
The journal retains 32 settled terminal automatic receipts plus active or
unresolved work under its existing 2 MiB bound. Unresolved recovery and cleanup
are never pruned to make room. Manual receipts retain their separate 256-row
capacity and retry/fence behavior; automation does not evict them. Broker-run
sequence and proxy-session fences prevent delayed submissions from becoming new
work after pruning or restart. See the
[E4 transaction contract](../services/nvpair-ui-broker/ENGINE_SETTINGS.md).

HTTP cancellation retires that request's waiter. If no waiter remains before
acceptance, new acceptance is cancelled. Once preparation is accepted, losing
the HTTP waiter alone does not cancel the node-owned operation: it keeps its
initial deadline and may finish or reconcile. Pause, scoped Off and authority
fences still apply. This is not a persisted inference queue or permission to
replay interrupted work through a replacement worker.

## Refusal and Retry

Preparation emits no provisional inference bytes, SSE heartbeat or stream splice.
A known refusal is HTTP `503` with the existing JSON admission error shape
(`code`, `error`, `reason`) and `X-PAIR-Admission`. Preparation reasons include
`engine-switch-timeout`, `engine-switch-busy`, `engine-switch-cooldown`,
`engine-locked`, `management-denied`, `model-unavailable`, `paused`, `draining`
and `no-fit`. Internal stale-revision or unavailable preparation results become
`model-unavailable` at HTTP; native error text is not forwarded.

`Retry-After: 1` accompanies timeout, busy, cooldown, draining and no-fit
refusals; paused uses `Retry-After: 30`. Resolve locks, permissions or missing
models before retrying those refusals. Failover is possible only before output,
inside the original eligibility and time bounds. No eligible inventory or
supported offer keeps the ordinary no-owner `502`; concrete tiers retain their
existing no-model `404`.

`X-PAIR-Switch-Request-Id` is present when a known switch receipt request ID
is available. It can also name a durably rejected attempt: read the existing
switch status to establish acceptance, phase and outcome. The header alone is
not acceptance proof. An unknown acceptance must not become a fresh automatic
submission, and absence of the header does not prove that no work was accepted.

The private `X-PAIR-Engine-Prepare-Budget-Ms` carries decreasing time only on
authenticated PAIR hops and supplies no authority. Absence uses the normal
bound; excess is clamped to 90000 milliseconds. Malformed, repeated,
noncanonical, overflowing or nonpositive values allow no preparation. Private
headers are stripped before local or directly configured manual engines. Final
`X-PAIR-Model`, `X-PAIR-Engine` and `X-PAIR-Node` describe actual execution.

## Client and Process Proof Status

Desktop and TUI already display **Automatic engine switch** for marked receipts,
using existing E4 phases, errors, observations and readback. They do not
coordinate stop/start or infer completion from target readiness.

### Desktop Binding Editor

In the selected node's **Routing & resources** form, use **Model engine
bindings** to add a row, choose an engine and type its native model name. Engine
choices use that node's descriptor labels. Suggestions contain only models
observed for that node and engine; they are not a complete inventory. Type a
native name when a stopped engine has reported no models.

Add, edit, **Remove** and **Clear bindings** change only `engineBindings` in
the existing **Policy** JSON draft. Clear writes an explicit empty array.
Unrelated fields, including unsaved private routing/account edits, remain in
the draft. Malformed JSON or binding rows disable the binding controls and keep
the original text for correction, rather than rebuilding a policy from defaults.

Use the same **Save** action and CAS/readback/error flow described above. The
form guards against a changed target and clears the previous target's draft;
obsolete reads or save replies cannot replace the new target's draft. Conflicts,
unsupported targets, management denial, pause vetoes and uncertain saves remain
explicit. Saving starts nothing, and a saved binding does not establish runtime
readiness. Existing switch controls display automatic receipt phases and errors;
the binding editor adds no lifecycle command, progress owner or separate draft
store. There is no TUI or bulk binding editor.

See the [desktop API contract](../desktop/docs/frontend-api.md#model-engine-bindings-in-routing--resources)
and [editor regression tests](../desktop/tests/modular/model-engine-bindings-editor.test.tsx).
Reported Task 6 Windows automation passed the focused suite (451 tests,
including 15 new editor cases) and full unit suite (2357 passed, 13 skipped).
The Mac merge gate repeated the focused suite and static checks. These are
automated results; native GUI and assistive-technology acceptance remain
**pending, not observed**.
