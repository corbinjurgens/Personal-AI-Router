# Measured run performance

Expand a node's performance view to see measured runs below its hardware chart.
In the TUI, open node detail and press `v` for the measured-performance view.
Scroll with the arrow or Page Up/Page Down keys; press `v` to return to the
engine and model controls.
These are broker-owned cached aggregates of actual local engine executions,
grouped by measuring host, actual serving engine, concrete model and effective
serving profile fingerprint. Quantization, engine family and context tokens
describe that profile when known. Different profiles stay separate.

This view only displays reported measurements. It does not run benchmarks,
estimate throughput, rank nodes, sort by speed or change scheduling. The
proxy records actual local inference attempts at their executing destination,
including direct and reverse peer ingress. The forwarding origin does not count
another local execution. Missing required engine/model identity suppresses
samples; an empty measured-run section can therefore remain expected. Hardware
utilization history is independent of execution measurements.

Streaming measurements use the proxy's existing response reader. llama.cpp and
Strata Chat completions preserve reviewed engine-native timing semantics;
Ollama native streaming retains its count/duration measurements. Nonstream
responses have unknown protocol/numeric evidence in this milestone. The serving
fingerprint includes the joined engine runtime, settings, launch and model-content
identity, effective request options, API and timing schema. Identity changes
separate profiles; changes during execution drop the observation. No placeholder
identity or response model field qualifies a measurement.

The proxy queues a bounded window of samples and drops telemetry when full.
One sender writes notifications without holding the queue lock or making the
inference producer wait for codec IO. Shutdown stops it between writes; an
already active codec write follows the existing notification lifetime.

Fresh, Stale and Unknown describe the broker's knowledge of the measuring host's
summary. A missing summary is Unknown. Last seen age describes host reachability;
the newest and oldest sample ages describe the measurements themselves. A fresh
host can still report old samples. Clock uncertain marks a source whose sample
clock cannot be treated as reliable. The UI displays the broker's snapshot ages
and does not run a separate aging timer.

Latency rows show median and p95 with their contributing sample coverage. TTFT
means the first protocol-defined output token; response headers and the first
body byte are separate observations and are not token evidence. Admission wait
is measured before an execution ticket is granted; engine load comes from the
engine's reported duration. Latencies are displayed in milliseconds.

Prefill and legacy decode rates divide exact engine-reported token totals by
their matching phase-duration totals. **Engine-reported decode** instead shows
the duration-weighted mean of qualified reported native rates:
`sum(rate * engineDecodeNs) / sum(engineDecodeNs)`. It preserves rounded engine
rates without reconstructing an integer native work count. For example, 400 ms
at 55 tokens/s and 600 ms at 45 tokens/s produce 49 tokens/s, independently of
visible output counts. Its coverage counts only samples with both a positive
engine interval and a reported rate, completed transport and confirmed protocol
completion. Failed, cancelled, incomplete and unknown-protocol samples do not
contribute. A known interval without a rate remains unknown speed.

The decode row prefers this reported aggregate when present; otherwise it shows
the legacy count-derived aggregate. These populations are never combined.
Each rate has its own coverage supplied by the broker.
The UI never divides estimated token counts by wall-clock latency. `--` means
unknown or absent; a measured zero remains `0`. Coverage shows contributing
samples over all samples for the profile. Completed, failed and cancelled are
transport outcomes; protocol incomplete separately counts completed transports
whose expected protocol end was known to be missing.

The coordinated telemetry schema is version 2 across the broker, peer relay,
desktop and TUI. Samples add nullable `engineDecodeNs` and
`engineDecodeTokensPerSecond`; summary entries add `engineDecode` with `samples`,
`durationNs` and `tokensPerSecond`. Existing `outputTokens`, `decodeNs` and
`decode` retain their exact count/matching-interval meanings. Native llama.cpp
decode steps and Strata internal work can differ from visible output, so daily
adapters must keep these separate and include timing semantics in the serving
profile fingerprint. Older summary versions and peer capabilities are rejected;
there is no dual protocol. All machines must update together.

The persistence file layout remains version 1. The upgraded reader preserves
valid history without the optional new fields and round-trips new measurements.
Older binaries cannot safely reopen upgraded history: use separate candidate
data for rollback validation, never the installed history. Native MSI llama.cpp,
MSI Strata and PC3 llama.cpp evidence, trustworthy non-Ollama identities and
end-to-end propagation acceptance remain pending. Deterministic producer checks
do not establish daily-engine acceptance.

Each summary replaces that host's previous aggregates. Repeated snapshots do not
add to totals. Omitted profiles were excluded from the published summary;
expired profiles were removed from its current projection. Local eviction
counters, when available, describe profiles, samples and expired samples removed
from the local store. These limits mean the displayed totals are a retained
window, not lifetime request counts.

Persistence degraded warns that cached measurements may not survive restart.
Publication blocked means the local summary cannot currently be published.
Peer summaries are accepted only through the admitted-peer trust boundary;
admission establishes the source identity, not the honesty or comparability of
its benchmark claims. No prompts, response bodies or pairing secrets are shown
in this section.
