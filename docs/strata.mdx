# Using a Prepared Strata Runtime

[Strata](https://github.com/Niko1221/Strata) is a native inference engine with
a Python HTTP server in front of it. This page describes how to point Personal
AI Router (PAIR) at a Strata installation that you have already prepared by
hand, and what PAIR does and does not do with it.

This is an experimental, operator-driven setup. PAIR does not install,
download or update Strata, and it has not been qualified on real hardware:
launch, GPU use, cleanup on stop and cancellation behavior all still need
owner-approved testing on the machine that will run it.

## What PAIR does with Strata

PAIR treats Strata as its own engine, not as a renamed llama.cpp. It is
declared by a user manifest, which `nvpair-engine-manager` reads, rather than
by a built-in entry. The manifest's descriptor is also what the proxy and the
broker use to front it.

| Area | Today |
| --- | --- |
| Start, stop, health | `nvpair-engine-manager` runs the prepared server as a process on `127.0.0.1` and waits for `/health` to return HTTP 200 with `service` equal to `strata`. |
| Model inventory | `/v1/models` is read for `data[].id`. Only rows whose `status.value` is `loaded` count as resident. |
| Load and unload | `POST /v1/load` and `POST /v1/unload` with `{"model":"<id>"}`, with response budgets of 600 and 30 seconds. |
| Published protocol | `openai-chat`: `POST /v1/chat/completions` and `GET /v1/models`. No legacy completions, embeddings, Anthropic Messages or Responses. |
| Model names | Exact. `name` and `name:latest` are different models. |

Server health is not model residency. The template starts Strata with
`--lazy`, so the server can be healthy and answering `/v1/models` while no
model is loaded. A first load can take minutes; load and unload are separate
operations from start and stop.

### How the proxy fronts Strata

`nvpair-proxy` has a compiled table for Ollama, LM Studio and llama.cpp only.
Any other engine is fronted from its descriptor, and Strata takes that path.
When PAIR starts, the broker reads the engine descriptors once. It fronts every
engine that is available on the host (the manifest defines the host's platform)
and that the proxy can serve, which for Strata means its `openai-chat` protocol.
For Strata that gives:

- A facade in the one proxy process. It has no stock client port. The broker
  plans one upward from 18180, and the proxy persists where it landed in
  `strata-proxy-port.json` in the per-user data directory, so the port stays put
  across restarts. The broker logs `fronting descriptor engine` with the planned
  port.
- A cluster service key, `e-strata`. It is registered while engine-manager
  reports Strata running, and withdrawn when it stops. It travels over the
  authenticated peer-services path and the reverse transport, never in the mDNS
  record, so peers can route to the node only once they are paired.
- A model list read from `/v1/models`, which is also the health probe for the
  advertisement.

The set of fronted engines is fixed when PAIR starts: a new or edited manifest
takes effect at the next start. There are no engine settings for Strata in the
desktop application and no `strata-proxy:` client relay yet. Cross-machine
routing of Strata requests has not been tried on real machines.

`services/nvpair-proxy/strata_profile_test.go` builds the descriptor from the
template and pins what the facade does with the `openai-chat` surface:

- `POST /v1/chat/completions` is inference. It is routed only to a node that
  advertises the requested model, forwarded byte for byte (streamed responses
  included) and tracked as a workload. A model no node advertises is refused
  with 502 and never reaches the engine.
- `GET /v1/models` is merged across nodes in the OpenAI list shape, one row per
  model id, keeping each engine's own row fields such as `status`.
- Every other path is forwarded verbatim as ordinary traffic. The proxy does
  not refuse it, does not check the model against a node's inventory and does
  not track it as a workload. Whatever the engine answers, including its own
  404 for an unsupported path, reaches the client. That includes `/v1/load` and
  `/v1/unload`: without an API key a client of the facade can load and unload
  the model; with one, those paths carry only what the client sent, so the
  engine refuses them unless the client has the key itself (see below).
- Enabling the facade without a descriptor, without a port, or for a descriptor
  with no chat and model-list protocol is refused.

The inventory a node advertises is the configured model list, loaded or not.
Load the model first; whether Strata loads an unloaded model on the first chat
request under `--lazy` was not checked.

## The Strata API key

A prepared config may set `api_key_file`: the absolute path of a regular file
holding one key (16 to 512 printable ASCII characters, no spaces or commas,
optionally followed by one line end). An inline `api_key` is rejected, because
the config's bytes are hashed into fields PAIR shows to clients, and a weak key
could be guessed offline from those hashes. The key file is never hashed, never
a declared artifact and never forwarded to the server; PAIR binds it by
identity (path, size, modification time and file ID), so replacing it requires
a fresh approval and restart.

Moving the key the fork's preparation wrote into the config is a one-time step:
copy the `api_key` value into a new file next to the config (for example
`strata.key`), restrict that file to your user, replace `"api_key": "..."` with
`"api_key_file": "<absolute path to strata.key>"`, and approve the changed
config. Two residuals are accepted: the file's size reveals the key's length,
and a rewrite that keeps the same file, size and modification time is not
detected. A missing, empty, unreadable or oversized key file, or one that does
not hold one key, fails the preview with a message that never repeats its
content.

The key stays on the serving host:

- engine-manager gives it to the Strata server only as `STRATA_API_KEY` in the
  server's environment; it is not in the launch snapshot, readback or logs;
- engine-manager's own requests (model list, load, unload) carry it, never
  follow a redirect with it, and redact it from error bodies;
- the broker reads it from engine-manager over a private method that clients
  cannot call, uses it for the advertisement health probe, and hands it to its
  own proxy over the private stdio channel;
- the proxy sends it only to this node's own engine, and only for chat
  completions and model-list reads, from local clients and admitted peers. It
  replaces any `Authorization` or `X-Api-Key` the caller sent. Every other path
  is forwarded with only what the caller sent.

The key never enters engine descriptors, discovery, peer payloads or the
desktop application, so peers route to the node through PAIR without knowing
it. A missing or wrong key is the engine's own 401; there is no
unauthenticated fallback. Changing the key changes the approval digest, so it
takes a fresh approval and restart. Loading and unloading remain available
through PAIR's engine controls.

## Unsupported actions

These are not available for Strata, and no PAIR setting enables them:

- Install, update and uninstall. Strata's own setup is interactive and
  downloads files; PAIR does not run it.
- Model pull (download), model delete and model copy between nodes. The model
  files belong to the prepared installation. Each Strata server instance has
  one configured model, so `/v1/load` selects that model rather than an
  arbitrary one.
- Legacy completions, embeddings, Anthropic Messages (`/v1/messages`) and
  Responses (`/v1/responses`) as PAIR-classified inference. Strata serves some
  of these upstream, but PAIR does not claim them for Strata.
- The optional Strata features: request monitoring, before-load hooks and MCP
  hooks. Leave them disabled in the configuration.

## Finite prepared serving record

An optional version 1 `runtime.serving` record binds one exact model to reviewed
native context, parallelism, placement, output and declared memory bounds. The
adapter supports the narrow native subset inspected at `corbinjurgens/Strata`
`f6726098`, extended to the current fork profile described below; that source
does not identify an installed MSI executable. See the
[adapter contract](../services/nvpair-engine-manager/spec.md#finite-prepared-strata-launch)
for accepted config keys, flags and artifact roles. Unknown modes, automatic
fitting, ambiguous clamping, duplicate options and undeclared explicit file
dependencies are rejected before spawn or settings persistence.

Declare every selected shard, pack/draft file, profile, tokenizer file, Python
executable, server script, config, native executable and attested library.
Runtime files use cached full SHA256 verification. Model artifacts keep the
operator-supplied full SHA256 plus bounded samples, size, mtime and resolved
target checks. Declared model targets and runtime paths ending in `.gguf`,
including split GGUF names, are excluded from runtime hashing. Other declared
runtime files are fully hashed before the lifecycle lock, with cancellation;
under the lock only bounded bindings and cached file metadata are rechecked.
Pack/draft enumeration is
fixed; a main pack may name its experts through `native_experts.txt` instead of an
`experts.bin`, and a draft pack may not. All paths must be
absolute and existing; directory and selected file spellings must be clean and
use the platform's native separators. The hashed config binds the `lib_dirs` list,
but directory contents are never crawled or hashed. Undeclared libraries reached
through those directories or inherited PATH/LD_LIBRARY_PATH and Python imports
beyond declared files remain unattested, as readback states.

Preview returns an approval digest without probing, loading, spawning or writing
a snapshot. Apply requires that digest and unchanged file bindings; start
rechecks them and launches from a small immutable config snapshot referencing
the original model files. Lazy HTTP startup remains distinct from loading.
Readback distinguishes configured and owned-launch-validated bounds; loaded
observations, strict content qualification and real Windows/GPU acceptance remain
unverified. This record does not implement automatic residency.

## Current Strata fork compatibility

The adapter was written against `f6726098`. The owner's current fork
(`corbinjurgens/Strata`, `main` at `0e70753c6b0668ecf929d8ee52982a2922b4e727`)
generates a different launch profile, and the adapter now accepts most of it. The
`TestStrataCurrentFork` tests in `services/nvpair-engine-manager` pin what is
accepted and rejected against the sanitized
`testdata/strata/current-fork-contract.json` (fake key, placeholder paths). They
call the parser and compiler only: no server, engine or installed port is
contacted, and nothing here shows that the current fork runs under PAIR.

Two things keep the generated profile rejected as a whole: `memory_policy` and
the inline `api_key`. A profile prepared as a separate, fixed candidate, without
`memory_policy`, with the key moved to `api_key_file` and with a fixed expert
cache and prefill, is accepted. Deleting fields to
make validation pass is the operator's explicit act of preparing that candidate,
not something PAIR does.

What the generated profile for the low-VRAM 128K case contains, and what the
prepared launch does with it:

| Generated item | Now |
| --- | --- |
| `log`, `env`, `gpu`, `fit_max_tokens` | Bound: validated and forwarded to the server in the immutable snapshot. `log` is an absolute clean path in an existing directory, a regular file that is not the same file as any declared input; `env` is a closed list of the four memory controls (`STRATA_RESIDENT_HEADROOM_GIB`, `STRATA_FILE_CACHE_MIB`, `STRATA_FILE_CACHE_COMPACT`, `STRATA_OWNED_PRICE`) with their value syntax, shown in the approved placement; `gpu` is a small non-negative index; `fit_max_tokens` is not an output guarantee |
| `build_metadata`, `gpus_asked`, `port`, `open_browser` | Validated and not forwarded: the server does not read them, or PAIR's command line decides. `open_browser` must be false |
| `host` | Must be `127.0.0.1`; the command line host wins; not forwarded |
| `--kv`, `--kv-resident`, `--resident-budget-gib` | Accepted with their value syntax (`fp16`, `int8`, `q4_0`, `q4`, `k8v4` for `--kv`; a positive plain decimal in GiB for the budget) |
| `--suffix-draft`, `--lookup-chain` | Accepted only as an explicit `0` |
| `--no-prefill-borrow` | Accepted as a value-less flag |
| `--serve` | May be omitted from `args`: the server prepends it |
| `native_experts.txt` in the main pack | Bound with the shards it names when the pack has no `experts.bin`; both together are rejected as an ambiguous expert source |
| keys that differ only by case | Rejected, at the top level and inside `env` |
| `memory_policy` | Still rejected: the server recomputes launch controls at startup from live telemetry, so approval would have to bind the effective result, and how to do that is an open design choice |
| `--expert-cache auto`, `--prefill auto` | Still rejected, with `memory_policy` |
| `api_key` | Rejected inline; move it to the file `api_key_file` names, see [The Strata API key](#the-strata-api-key) |

Inventory rows with `status.value` of `loaded` count as resident; a missing,
unknown or `loading` status does not.

Not exercised: load and unload responses, authentication failures,
cancellation, redirects and any request through the proxy. The recorded owners
of the credential path are listed in the fixture and checked to still exist.

## Procedure

1. Prepare Strata outside PAIR, using its own setup, until its generated launch
   script runs the model from a terminal. Note the absolute path of the Python
   interpreter for that environment, of `serve/server.py` and of the prepared
   configuration file.
2. Copy `services/nvpair-engine-manager/testdata/strata/strata.json` to
   `strata.json` in the per-user `engines/` directory. The directory for each
   operating system is listed in the
   [manifest reference](../services/nvpair-engine-manager/MANIFEST.md#where-manifests-live).
3. Replace every `/REPLACE_WITH_ABSOLUTE_PATH/` value:
   - `runtime.bin` is the Python interpreter.
   - The first `runtime.args` entry is `server.py`, and the argument after
     `--config` is the configuration file.
   - `runtime.editable_launch.fixed_args` uses that same `server.py` path.
   - Each retained platform's `detect` entry is the `server.py` path. Delete
     the platforms you do not use.

   Arguments are literal strings. Do not use environment variables or `~`, and
   escape backslashes in JSON on Windows. Keep `--host 127.0.0.1`,
   `--port {port}` and `--lazy`, and choose a free `runtime.port` (the template
   uses 18082).
4. Restart PAIR so `nvpair-engine-manager` reads the manifest and the broker
   fronts the engine. A manifest it cannot parse is logged and skipped rather
   than stopping startup.
5. Check the engine through engine-manager: `engine:descriptors` should list
   `strata` as available with protocol `openai-chat`, `engine:start` should
   return once `/health` reports the Strata service, and `engine:models`
   should list the configured model under `modelsByEngine` but not under
   `loadedByEngine` until you load it with `engine:load-model`.
6. Find the facade port in the broker log line `fronting descriptor engine` or
   in `strata-proxy-port.json`, then send a chat completion for the loaded
   model to `/v1/chat/completions` on that port.

The fixture tests check this contract against loopback fakes only. They do not
start Strata, and the platform entries in the template are not evidence that a
platform works. Strata documents Windows and Linux with NVIDIA CUDA as its
primary path and macOS as an experimental Apple Silicon source build; confirm
your hardware against its documentation first.
