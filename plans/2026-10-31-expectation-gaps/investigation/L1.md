# L1 — Roles and tiers: how hard-coded are they, and what would user-defined roles with multiple profiles per role need
Baseline: integration/join33 4eccd05d. Investigated: 2026-10-31.

## Verdict
The tier vocabulary is a closed, ordered set `weak < medium < strong` defined once in Go (`nodepolicy.TierOrder`) and mirrored once in the desktop (`ROLE_TIERS`), but about 15 further places (Go and TS) spell the three names literally: switch statements and fixed enums in routing history, a hand-written list of the six `-api`/`-local` aliases, a separate `isTier` in `shared/modelconfig`, the model-settings UI, and UI labels. Routing depends on the order (`tierSearchOrder` for `allowStronger`/`allowWeaker`, `tierRank` in the sort and reservation class). A node declares at most one `(engine, model)` per tier (`Policy.Roles map[string]Role`), and policy validation allows at most one `Profile` per `(engine, model)`, so "multiple profiles per role" and "two profiles of the same model" are both impossible today. The desktop shows a role as the raw inventory model name plus the engine label (`roleLabel` -> `"${role.model} (${engine})"`), which for llama.cpp router presets is the preset section name (for example `joes-tiel35b-udq4kxl`), not the model's identity or quantization. A role-name set shared across the cluster has no home. The nearest existing mechanism is the union of the roles that nodes advertise (`declaredRoles.peerTiers`).

## Findings

### Q1. Where the vocabulary is hard-coded (count and list)

### Q2. Data model
- `Policy.Roles map[string]Role`, `Role{Engine, Model}`. This is a **per-node** declaration (device field; peer-editable through `PeerProjection`/`MergePeerSet`, `projection.go` `PeerPolicy.Roles`). `Role` is also reused as the element type of `ServedModels`/`ResidentModels`.
- `Policy.Tiers map[string][]TierEntry`, `TierEntry{Kind local|api, Engine, Model, ContextTokens, Capabilities, Deployment}`. This is **router-side**: the ingress node's own guesses about models in the cluster. Peers can see only local entries (`projection.go` `localTiers`), and `MergePeerSet` restores `stored.Tiers`, so a peer cannot change them.
- `Policy.TierPolicy{AllowStronger, AllowWeaker bool; PreferLoaded "tier"|"any"}` is **router-side**, as is `Routing.Tiers map[string]TierRouting{BareMode, AllowedFamilies...}` (origin-only).
- `Profile` fields, exactly: `Name, Engine, Model, Quantization (omitempty), ContextTokens, Capabilities, MemoryBytes, MaxConcurrent, RequestOptions (json.RawMessage), RequestOptionsMode, LocalOnly, MaxOutputTokens, Qualification *QualificationRef`. Per node. `Name` matches `^[A-Za-z0-9][A-Za-z0-9._:/-]{0,127}$` and must be unique. Only one profile may cover a given `(Engine, Model)`. No launch settings (context flag, n-cpu-moe, etc.) live here; those live in engine settings or the llama.cpp preset. `Quantization` is free text and is not read by routing.
- `Advertisement{ServedModels, Revision, Roles map[string]AdvertisedRole, PausedBy, StrictAdmission, EngineBindingOffers}` and `AdvertisedRole{Engine, Model, ContextTokens, Capabilities, MaxOutputTokens, Qualification}`. Published per node. `Policy.Advertisement` fills bounds from `ProfileFor(role.Engine, role.Model)`. A role with no profile advertises no context bound, which `metBy` treats as unbounded.
- Interaction in `resolveTierCandidates`: for each tier in the search order it (1) takes every distinct `(engine, model)` declared for that tier by self or any peer (`declaredRoles.forTier`), resolves candidates on that model, and keeps only nodes whose own declaration for that tier matches and meets the request's needs. Then (2) it walks the router's `pol.Tiers[t]` local entries and adds a candidate **only if that node declares no role at all** (`len(declared.of(c)) == 0`). API entries are skipped. A node that declares any role is therefore authoritative for every tier (C9). Why "Joes needed both": the source does not support that the tier entry was needed. Joes declared `roles.medium` (r14), so its own router entry for medium cannot apply to Joes itself. The entry's `contextTokens 32768` would only bound non-declaring nodes that have a model with the exact name `joes-tiel35b-udq4kxl`. The role's context bound instead comes from a `Profile` with the same `(engine, model)`, if one exists (C11, inferred; not live-checked). The overlap is real as UX: two places to say "this model serves medium", with different scopes (node vs. router) and different context sources (Profile vs. TierEntry).

### Q3. Ordering semantics
Order is load-bearing in four places: `tierSearchOrder` (stronger and weaker fallback by index distance), `tierRank` (sort key and hard class in `reserveRoundPrepared`; the smart-routing plan also keeps tier rank as a hard class), `configuredAliases` listing order, and the doc of `TierOrder`. With arbitrary names, `allowStronger`/`allowWeaker` would lose meaning. They would need either an explicit ordered list of role names (a strength rank) or a per-role fallback list (`fallback: [roleB, roleC]`). Either one replaces `tierSearchOrder`'s index arithmetic, and the rest of the pipeline (`tierRank` int) is unchanged. Additional constraints for free-form names: they share the request `model` namespace, so a role name must not collide with a real model id, must not end in `-api`/`-local` (`ParseAlias`), and is rejected as a model id where `IsReservedAlias`/`modelconfig` checks apply. Routing history stores tier as a small fixed enum (`routing_facts.go`, `routing_events.go`, `routing_wire.go`, desktop `routing.ts`), so it would need a string field or a bounded name table.

### Q4. Multiplicity
- One role on a node names exactly one `(engine, model)` (C7). A role cannot point at several.
- One tier can resolve to several models on the same node only through **router entries** on a non-declaring node: each `pol.Tiers[t]` entry the node has installed adds a candidate. Fallback tiers (`allowStronger`) also add the same node's other-tier models at a higher rank.
- Dedup key: `c.id + "\x00" + c.engine + "\x00" + normalizedModel`. The first insertion wins, which is the requested tier (lowest rank) and the declared role over the router entry. `candidate` carries `model`, `tierRank`, `declared`, `warm`, `preparation` (`proxy.go` `candidate`). Two profiles of the same model on the same node would collapse under this key, and validation already forbids them (C8). In practice, multiple configurations of one GGUF exist today only as differently named llama.cpp preset sections, which become different model names. That is why context and node names end up in model names (inferred from vault r14 and `roleLabel` showing inventory names; `--models-preset` handling in `nvpair-engine-manager`).

### Q5. Display and editing
- `RoleEditor.tsx` (in `RoutingSettings.tsx`, per node): one `Select` per `ROLE_TIERS` entry with label `TIER_LABELS[tier]`. Items come from `roleItems(choices, ...)`, each `children: roleLabel(choice, descriptors)`. `inventoryChoices` takes `model.name` from that node's engine inventory (downloaded only). Label code path: `roleLabel(role, descriptors)` -> `engineLabel(engineTypeFromManagerName(role.engine), ...)` -> `` `${role.model} (${name})` ``. An installed value that no longer appears gets `", not installed"` appended. The Suggest button copies the first installed local tier entry (`suggestRoles`).
- `BulkNodeConfiguration.tsx`: `describeRoles` -> `` `${tier}: ${roleLabel(...)}` `` per tier. It has a select per tier per target that uses the same items.
- `NodeList/NodeDeclaredRoles.tsx`: tags `` `${tier}: ${roleLabel(role)}` `` from the discovery advertisement.
- `ModelSettings/ModelLoadSettings.tsx`: "`{tier} role currently: {JSON.stringify(routing.roles[tier])}`" with a per-tier Select. `ModelSettingsCopy.tsx` copies weak/medium/strong membership.
- None of these call `formatModelDisplayName`, and none show `Profile.Quantization` or a repo id. The user sees the raw engine model id (for llama.cpp router, the preset section name).

### Q6. Change size (facts for sizing, not a design)
- (a) **Cluster-defined role names.** No cluster store exists (roles-design.md §"Summary" item 5, "No cluster store"; bulk is client fan-out). Existing places a name set could come from: each node's `Roles` keys (already `map[string]...` on the wire in `Policy`, `PeerPolicy`, `Advertisement`, and desktop `NodeRoles` apart from its key type), and the router's own `Routing.Tiers`/`TierPolicy`. The proxy already computes the union of advertised names (`declaredRoles.peerTiers`) for `/v1/models`. Changes: Go nodepolicy validation/IsTier/ParseAlias/routing defaults (owner: shared nodepolicy, medium), proxy `tierSearchOrder` and the alias/borrowedAlias/filteredModels/history enum (owner: nvpair-proxy, medium), modelconfig `isTier` (small), routing-history wire on proxy, nodepolicy and desktop (medium, because the format is versioned), desktop types/ROLE_TIERS/labels/ModelSettings (medium), plus 65 test files (large mechanical). Overall **large**, mostly mechanical. The one design decision is where the ordered list or fallback lives: per router (like `TierPolicy` today) or copied to each node by the existing bulk fan-out.
- (b) **Multiple profiles per role per node.** `Role` would become a list, or a list of profile names. `Advertisement.Roles` value becomes a list (a wire change that older peers parse as malformed; `AdvertisedRole.UnmarshalJSON` is tolerant only per field). The `(engine, model)` uniqueness of `Profile` and `ProfileFor` would have to be relaxed or keyed by profile name. `resolveTierCandidates`' `declared.of(c)[t]` match and the dedup key would need the profile. The broker's `mergeModelPolicy` role toggling changes too. Owners: nodepolicy (medium), proxy tiers.go (medium; serialize with smart-routing work, which edits the same sort), broker modelsettings (small), desktop RoleEditor/Bulk/store (medium). **Medium to large.** Note that if "profile" keeps meaning "distinct llama.cpp preset model name", the router side already handles several distinct models per tier across nodes. Only the per-node one-role constraint and the display would change.
- (c) **Keep weak/medium/strong as defaults.** `Default()`/`defaultRouting()` already seed `routing.tiers` from `TierOrder`. If TierOrder became a default list rather than a closed set, existing policies stay valid unchanged (`Roles`/`Tiers` keys are strings). **Small** on its own, given (a).

## Mapping to owner expectations
- **E1 (user-defined cluster roles):** missing. The set is closed in Go validation (`Validate`, `ParseStored`, `Routing.validate`), dropped on receive if unknown (`filteredModels`, `parseNodeRoles`), and literal in ~15 sites. There is no cluster-level home for names. Each node already assigns its own model per role, which matches the expectation.
- **E2 (true identity display):** missing in role UI. `roleLabel` shows the raw inventory name. `Profile.Quantization` exists but is not shown and not tied to the role label.
- **E3 (profiles, multiple per role):** missing. One `Role` per tier, one `Profile` per `(engine, model)`, and Profile holds no launch settings (context comes from the preset, so it ends up in the name).
- **E5 (context advertising):** partial. Each declared role advertises `ContextTokens` from its profile, and `metBy` filters per request. No "highest across nodes" is computed, though candidates with larger context are eligible.
- **E12 (configure from one node, see where requests go):** roles are remotely editable (RoleEditor, Bulk). `tiers`/`tierPolicy` are not editable in the desktop (C14), and the node-wide authority rule (C9) is explained only in one line of UI copy.

## What a fix would have to touch, and what to reuse
- Reuse `Policy.Roles`/`Advertisement.Roles` (already string-keyed) and the R2 advertisement path (`Policy.Advertisement` -> engine-manager `/v1/models` -> scanner -> `DirectoryNode` -> proxy `Node.Roles`, desktop `policy.roles`). Do not add a new channel.
- Reuse `declaredRoles.peerTiers` as the cluster's observed role-name union, and the existing bulk fan-out (`node-configuration.store.ts`) to copy a name list or order to several nodes. Do not invent a cluster store.
- Replace `tierSearchOrder`'s index arithmetic with an explicit order or fallback list, and keep `tierRank` and the sort and reservation classes unchanged.
- Route every literal site through one `IsTier`/name-set function: Go `modelconfig.isTier`, `borrowedAlias`, `requestedDescriptor`, routing-history enums; TS `RoleTier`, `TIER_LABELS`, `model-config.ts`, `routing.ts`, `engine-settings.ts:85`, ModelSettings files.
- For display, extend `roleLabel` to use the profile (`Quantization`, plus a model identity source that is not yet present) instead of `role.model`, rather than adding a second label function.
- Sizes: (a) large, mostly mechanical; (b) medium-large; (c) small given (a).
