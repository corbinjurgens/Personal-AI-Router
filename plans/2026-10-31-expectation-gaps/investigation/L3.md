# L3 — Profiles: what PAIR calls a profile today versus the owner's profile (model + quant + engine + launch settings), and where llama.cpp per-model launch settings live
Baseline: integration/join33 4eccd05d. Investigated: 2026-10-31.

## Verdict
PAIR has two separate per-model records, both keyed by the exact native model ID. Neither has a separate profile identity. (1) The node-policy `Profile` in `<appdir>/node-policy.json` holds routing, admission and request data: name, engine, model, quantization, contextTokens, memoryBytes, maxConcurrent, requestOptions, mode, localOnly, maxOutputTokens and qualification. Validation allows at most one per (engine, model) on a node. (2) The engine-manager typed `ModelLoad` lives under `runtime.modelLoads` in `<appdir>/engines/llamacpp.json` and holds the llama.cpp launch preferences plus the target-resolved values. CanonicalLoads also allows at most one per model ID. Since 17c13ce2 the model-setup series (Task 6 O1 `13bfeef5`, Task 7 `b854cbb1`, Tasks 10-12) made coupled Preview → Apply (restart) of typed llama load settings work end to end through the broker, so the Framework note's "Apply refused" statement is out of date. The typed option vocabulary is a static Go table (`llamaServingOptions`, pinned to llama.cpp 7fe450e1). Nothing introspects `llama-server --help`. Only 14 fields are typed, and MoE/CPU-expert, tensor split, device selection, quantized KV, speculative and RoPE are visible but not editable. The owner's Profile needs several things that do not exist: a profile ID separate from the model ID, several configurations of one model, role → several profiles, user-defined roles (roles are hard-coded weak/medium/strong and map to (engine, model)), and one context value (policy `contextTokens` and typed `context` are separate and are not synced).

## Findings

### Q1. `nodepolicy.Profile`
Fields (`policy.go` `Profile`):
- `name`: unique label matching the `profileName` regex. No service reader beyond validation and peer projection. The desktop shows it ("Draft profile: X").
- `engine`, `model`: the key. `ProfileFor(engine, model)` does an exact match, and the model must already be normalized.
- `quantization`: free text with no reader (C4). Quant shown elsewhere comes from `performancewire.Profile` or is parsed from names (`format-model-display-name.ts`).
- `contextTokens`: routing and admission metadata. Readers: `Advertisement` (peer role context), proxy `local_qualification.go` bound, `residency.go`/broker `modelconfig.go` resident load options and envelope checks, `Validate` vs maxOutputTokens. It is not the native ctx-size.
- `capabilities`: tools, vision, structured, embeddings. Advertised per role and used for eligibility.
- `memoryBytes`: proxy `admission.go` `memoryLocked` budget, `readiness_contract.go` strict envelope.
- `maxConcurrent`: proxy `concurrencyLimitLocked`, strict readiness.
- `requestOptions` + `requestOptionsMode`: proxy `body.go` `transformBody` via `routing.go` `prepareCandidate`/`ingress.go`. These apply on the serving node only. They are bound into local qualification (`readiness_contract.go:140`).
- `localOnly`: `projection.go` `MergePeerSet` refuses peer writes that change options, mode or identity.
- `maxOutputTokens`: strict admission ceiling (`local_qualification.go`, `chat_adapter.go`). It is advertised.
- `qualification` {id, revision}: strict capacity install (`readiness_contract.go`), required for `residentModels`.

Two profiles for the same (engine, model) on one node: **no**, `Validate` refuses it. The only workaround is a different native model ID. That is a llama preset section alias, which is how names like `lfm2.5-24b-a2b-msi-ctx131072` come about (inferred from the section=modelId design in `typedLlamaPreset`/`parseLlamaServingPreset`).

### Q2. Per-model llama.cpp launch settings at 4eccd05d
- **Wire** (`modelconfig/wire.go`): `RequestedLoad` is portable intent where nil means inherited. `ResolvedLoad` is target-owned: perSlot/total context, slots, GPU layers, artifacts, NativeBuildID, PresetDigest, ReviewedInputID, DeviceBinding. `ModelLoad{ModelID, Requested, Resolved}`. `LoadPatch{Set, Clear}`. `PolicyPatch{Generation, RequestOptionsMode, Roles(map), Served, Resident, Binding}`. `ModelChange{ModelID, ExpectedPolicyRevision, Load, Policy, PreviewDigest, SupersedesRequestID}`. `InspectRequest{Engine, NodeID, ModelID}`.
- **Engine settings** (`shared/enginesettings/settings.go` `Config`): {WorkingSetLimitMiB, ServerPort, ProxyPort, LaunchText, Serving, ModelLoads}. `Request.ValidateModelChange` requires the target baseline echo. Portable edits come only through `modelChange`.
- **Compilation** (`modelsettings_load.go` `typedLlamaModelOptions`): maps to preset keys ctx-size (=per-slot×slots), parallel, gpu-layers, cache-type-k/v (f16 only), flash-attn, batch-size, ubatch-size, threads, threads-batch, kv-offload, op-offload, sleep-idle-seconds, cache-ram. It forces kv-unified=false, fit=off and load-on-startup=false. `typedLlamaPreset` renders the INI. When typed loads exist the router launches with the manager-generated `--models-preset`.
- **Inspect** (`modelsettings_rpc.go` `Executor.InspectModel`) resolves artifacts via `resolveLlamaArtifacts`, reads GGUF facts and returns `Options` (the descriptor matrix), `Estimate`, `ConfigurationKey` and memory profiles.
- **Apply**: the broker `previewModelSettings`/`reviewModelSettings` sends the load-only change to worker `engine:preview-launch`, merges the policy patch itself (`mergeModelPolicy`) and digests the review. `applyModelSettings` re-checks the digest, launch state, policy fingerprint, revision, TTL (10 min) and memory freshness. It then journals the accepted stage to `engine-settings-operations.json`, drains the engine and runs `runModelSettingsOperationLocked`. That calls worker `engine:configure-launch` (frozen resolved loads, `validateModelSettingsLaunch(applying=true)`), which stops, persists to the override file, rebinds and restarts. After that the broker commits the policy. **Public Apply is implemented** (Task 6 O1/Task 7 are not ancestors of 17c13ce2; verified with `git merge-base`).
- **Desktop end to end today**: Model Manager → Configure, or Routing → Configure model. Then: pick engine (llama.cpp / LM Studio) and exact native model text → optional "Create profile" (writes a `{name,engine,model}` policy entry into the shared draft; Save is separate) → generation fields → "Configure load and routing settings" → Basic load (context, slots, gpu, K/V precision) and Advanced (flashAttention, batch, ubatch, threads, threadsBatch, kv/op offload, sleepIdle, cacheRAM), plus weak/medium/strong role, served, resident and binding toggles → auto-preview (250 ms debounce) / "Preview model changes" (or "Recalculate" when Auto is selected) → "Apply reviewed model changes" restarts the whole llama.cpp router (60 s drain).
- **Files** (all under appdir): `node-policy.json` (Profile, roles, served/resident/bindings), `engines/llamacpp.json` (`runtime.modelLoads` requested+resolved, launch text, port), `engine-settings-operations.json` (broker journal and receipts), `serving/llamacpp/generation-*/models.ini` (ephemeral generated preset), `model-memory-profiles.json` (advisory stated/observed memory keyed by configurationKey).
- Auto: see C17. Descriptors and docs say it is unavailable in production. Code has a path that uses the broker's own memory telemetry. Status is unresolved here.

### Q3. Editors
- `RoutingSettings/ModelSettingsEditor.tsx` ("Model inference settings") edits only policy generation: temperature, top_p, top_k, min_p (llamacpp), repeat_penalty, frequency_penalty, presence_penalty, seed. It also has "Request overrides" (defaults/enforced) and "Only this device can edit generation settings". It shares the raw policy draft and Save with "Advanced policy JSON".
- `ModelSettings/ModelProfileControls.tsx`: create or remove the profile (name only).
- `ModelSettings/ModelLoadSettings.tsx` (the "model load settings editor"): the typed fields in `loadFields` (`node-policy-model-copy.ts`), rendered from the target's descriptors. Unsupported descriptors are listed read-only ("Advanced supported" / reason). It also has role, served, resident and binding toggles, Preview/Recalculate/Apply, `ModelSettingsPreview` (diff, impact) and `ModelMemoryEstimate`. This is a separate ModelChange operation, not the policy Save.
- Copy (`ModelSettingsCopy.tsx` + `node-policy-model-copy.ts`): generation copy requires an existing target profile ("Missing profile: Configure/Create on this target first"). `portableLoadPatch` copies selected requested leaves, and absent becomes a clear. Resolved values, paths, devices, locks, qualification and memory are never copied. The user types the exact target model ID, so the mapping is the user's own and equivalence is unverified. Each target gets its own preview/apply. Copying model content is a separate, user-chosen hand-off to Model Manager "Copy model files" and never triggers Apply.
- What it does NOT let you do: set contextTokens, memoryBytes, maxConcurrent, maxOutputTokens, capabilities, quantization or qualification (Advanced JSON only; positive control: `localOnly` is found in those components). It also cannot create a second configuration of the same model, name a configuration independent of the model ID, assign user-defined roles or several models per role, edit MoE, split, device, quantized KV, speculative or RoPE, or enter extra native options.

### Q5. Option introspection
There is no introspection. `llamaServingOptions` is a hand-written table pinned to 7fe450e1 (bundled B11146 per MANIFEST.md), and `validateModelSettingsOptionCoverage` checks only that descriptors match that table. Unknowns are handled by context:
- Parsed presets (serving declarations, conversion, buffer capture): refused.
- Conversion to typed: refused for any non-typed key.
- Typed editor: no extras field ("No raw extras field bypasses this matrix", MANIFEST.md).
- Raw launch text (`launchtext.go` `parseLaunchText`, Advanced engine settings): passed through to the engine, with arity guessed as 1.
- Override directory (`<appdir>/engines/<engine>.json`, `userPaths`): the engine manager reads the whole override, including `bin`, `args`, `launch_args`, `serving` and `modelLoads`. A custom fork binary can be pointed at there (inferred from `Runtime.Bin`/`Mode`). Its options are still judged against the 7fe450e1 table in typed and serving modes. The uninstall path honors only port and models_dir (`applyLocationOverrides`).

### Q6. Identity of a configuration
The key is the native model ID (`ModelLoad.ModelID`, `Profile.Model`). `configurationKey` (`model_configuration_key.go`) hashes resolved artifacts, build source, options+preset digest, placement and memory pools. It scopes advisory memory records only, and per its own comment is "never configuration identity or launch authority". `ReviewedInputID`/`PresetDigest` are review fingerprints. The only user-facing name is the policy `Profile.Name`, which is cosmetic (no service reader) and fixed 1:1 to the model. The broker auto-names profiles `model-<hash>`.

### Q7. Gap statement
Owner's Profile = {profile ID/name, display name/icon, model identity + quant, engine, launch settings, context, role assignments (many per role), copy to node with model copy}.
- Can reuse: engine-manager `ModelLoad.Requested/Resolved` (launch settings, resolver, preset generation, apply/restart), policy `Profile` (request options, admission bounds, qualification), the broker coupled operation (one review/apply across both stores), `portableLoadPatch` copy plus Model Manager content copy, and `InspectModel` facts and estimates.
- Genuinely new: (a) a profile ID independent of model ID. Today both stores key on modelId, so N configurations of one GGUF need N native aliases. The glue could be a profile ID → generated preset section alias, with the artifact binding to the real hub ID+quant. (b) A profile → model-identity record (repo + quant) instead of free text. `Profile.Quantization` is unused today. (c) User-defined cluster roles, and role → [profile IDs] on each node, replacing `Roles map[tier]Role{engine,model}` and fixed `TierOrder`. (d) One context source: typed `context` should derive `Profile.ContextTokens` (advertisement and admission), or the reverse. Today they are independent (C18). (e) Copy-as-deploy: copy profile → ensure model content (existing copy) → target preview/apply → role assignment, as one orchestrated flow.
- Compatibility: the earlier split (launch settings in engine-manager, request/routing in node policy, one composed editor, broker-coordinated apply) is compatible with a single user-facing Profile, *provided* the join key becomes a profile ID rather than the model ID. The broker `ModelChange` coupled operation is already the glue that atomically updates both. It needs a `profileId` and must emit the native alias. Nothing requires merging the two records into one store.

## Mapping to owner expectations
- **E2 (true identity, no context in name)**: missing. Keys are native model IDs (aliases). `Profile.Quantization` has no reader. A second configuration requires a new alias name.
- **E3 (profiles, multi per role, copyable)**: partial. Per-model settings exist and copy exists. Missing: profile ID, more than one per model, role → many, copy-triggers-model-copy-and-deploy as one action.
- **E4 (Unsloth-like editor + introspected extras)**: partial (table above). There is no introspection and no extras passthrough in the typed path.
- **E5 (context advertising)**: advertisement uses `Profile.ContextTokens`, which the typed editor does not set. Risk of divergence.
- **E1 (user-defined roles)**: the editor and policy hard-code weak/medium/strong (see roles units).
- **E9 (Profiles tab)**: missing. Configuration is reached per model from Model Manager or Routing.
- **E11 (estimate/validate)**: an advisory estimate exists, and configurationKey is a natural binding key for results. Validate is out of scope here.

## What a fix would have to touch
- `services/shared/nodepolicy/policy.go` (Profile ID, role → profiles, drop the (engine, model) uniqueness or move it to profile ID; `Advertisement`, proxy `admission.go` `profileLocked`, `readiness_contract.go`, `projection.go` `MergePeerSet`, keyed by (engine, model)). Large.
- `services/shared/modelconfig/wire.go` (`ModelLoad`/`ModelChange` gain profile ID / alias mapping) and engine-manager `typedLlamaPreset`/`resolveLlamaArtifacts` (section alias ≠ artifact identity). Medium-large.
- Broker `modelsettings.go` `mergeModelPolicy` (stop auto-naming `model-<hash>`, sync ContextTokens from the resolved per-slot context). Small-medium.
- Typed option coverage: add typed n-cpu-moe/cpu-moe, tensor-split/device, quant KV (validated), draft. Each needs identity and estimate support in `llamaModelSettingsOptions`/`typedLlamaModelOptions`/`convertTypedLlamaOptions`. Medium per group.
- Introspection: new engine-manager probe of `llama-server --help` per build, feeding descriptors as "extra/unvalidated" with a passthrough lane. This must be reconciled with the deliberate "no raw extras" rule in MANIFEST.md. Medium; needs an owner decision.
- Desktop: a new Profiles view. Reuse `ModelSettingsPanel`/`ModelLoadSettings`/`ModelSettingsCopy` and the `engine-settings.store` preview/apply rather than duplicating them. Medium-large.
- Reuse, do not duplicate: the broker coupled review/apply journal, `portableLoadPatch`, Model Manager content copy, `InspectModel`, `configurationKey`.

## Open questions / not verified here
- Whether production Auto actually resolves (C17). Docs and descriptors say no; code has a broker self-memory path. It needs a running node.
- Whether a typed `ModelLoad` can be created for a model ID that has no existing preset section or receipt (canonical-cache resolution) — inferred yes from the `resolveLlamaArtifacts` comment, not exercised.
- Whether a custom fork binary set via override `bin` passes typed compilation (`reviewedSource`/build checks). Not verifiable without engines.
- Restart impact on other models in the same router, and drain behavior, were read from docs and code only. Not run.
