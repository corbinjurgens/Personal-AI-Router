# L4 — Engine on/off, locks, switch, pause and the owner's Halt: what exists, what the owner wants removed, and what multi-engine concurrency allows
Baseline: integration/join33 4eccd05d. Investigated: 2026-10-31.

## Verdict
The core of the owner's Halt already exists: since stop-pause t1-t7, `node:set-availability {state:"paused", pauseMode:"immediate"}` is a local-only request. The broker accepts it only with an empty caller and local origin. It fences admission at once, cancels active work without a drain wait, reroutes uncommitted requests to other nodes, stops every controlled engine and proves each stop, and only a local Resume lifts it. What is missing compared with expectation 10:
- The button is a small primary "Stop local models now" button in the self node card, in Routing settings and in the tray, not in the toolbar (`AppBar.tsx`).
- It does not force-unload engines that PAIR does not own. An adopted Ollama or LM Studio leaves the Pause "incomplete" by design (owner Q5, 2026-10-28).
- The peer-controllable "simple on/off" is today's configured "Pause node". A peer can turn it off but can never turn it back on. Only a local Resume undoes it.

Engine On/Off switches and padlocks appear on every node card (`NodeEnginesInline.tsx`) and again in the engine settings (`BackendHeader.tsx`). The lock spans about 60 non-test files plus about 26 Go and 7 desktop test files. No per-role gate exists.

Several engines may run at the same time; nothing in engine-manager makes them exclusive. Two assumptions limit this, though:
- The default policy allows one resident model in total, across all engines (`MaxResidentModels: 1`).
- Bound-engine cold activation treats any other running engine as a conflict to switch away (E4) and refuses when more than one other engine is running.

The engine "switch" (E4) swaps which engine runs (stop source, start target). It does not switch models.

## Findings

### Q1: Off, Lock, Pause, immediate stop, and the owner's Halt
**Off (saved intent).** `nvpair-engine-manager/desiredstate.go` `desiredStateStore.set`/`Executor.setDesiredEnabled` save `enabled` with an origin (`local` or `peer`). Saved On engines are restored at startup (`RestoreEnabled`) and are eligible for wake. Since the 2026-10-23 decision, Off no longer blocks a managing peer: `nodeprojection.go` `remoteVeto` checks only pause and lock. A local Stop that races a peer start cancels that start with `-32011` (`engineOffVeto`), but it does not refuse later starts.

**Lock.** `enginelock.go` `setEngineLockedCommand`:
1. Saves `locked` together with local Off (`desiredStateStore.setLocked`).
2. Cancels remote work, an in-progress start, a crash relaunch and serving loads.
3. Reclaims or stops the engine and requires verified termination.

`activationVeto` (local) and `remoteVeto` (peer) both refuse a locked engine with `-32013 engine_locked`. Only the local path can change a lock (`engine:set-lock` has no peer route, and the bridge refuses a remote nodeId). Unlocking leaves the engine Off.

**Pause (configured).** The request is `node:set-availability {state:"paused"}`, with `pauseMode` omitted or `"configured"`, from a local client or a granted peer (relayed through `engine:remote-availability-set` / `POST /v1/node-availability/set`). `pauseNode` runs these steps:
1. Persists `paused` with `pausedBy`.
2. Pushes availability to the proxy, which then refuses new work with 503 `X-PAIR-Admission: paused`.
3. Waits out the configured drain (`finish` with a 120 s default, or `cancel`) and the 10 s cancel settle.
4. Calls `pauseEnginesOn`, which issues a parallel intent-neutral `engine:sleep` for every engine it knows and requires `terminationVerified`.
5. Publishes `paused`.

`managementBlocked`, projected to the engine manager, makes `activationVeto` and `remoteVeto` refuse every start, load and switch (local and peer) until a local Resume. A peer can start a pause but cannot repeat it or Resume it.

**Immediate local stop (t4/t5).** The desktop calls `window.pairApi.nodePolicy.setAvailability({state:"paused", pauseMode:"immediate"})`, which becomes WS/IPC `node:set-availability` to the local broker (`ui/stores/node-configuration.store.ts` `requestAvailability`; `ui/api/pair-api.ts` L299). The broker side:
- `setAvailabilityRequestAs` rejects the request unless the caller is empty and the origin is local.
- `acceptAvailabilityLocked` sets live `draining` and `cancelActive=true` before taking any lock.
- `runAcceptedAvailability` pushes availability to the proxy and persists before taking the transition lock.
- `pauseNode` skips the drain wait. It still runs `vetoRemoteEngineSwitch`, `supersedeInstallStartsLocked` and `cancelRemoteSwitch`, then the same `pauseEnginesOn` stop with proof.
- An immediate request can supersede a configured pause that is still draining (store L1038-1046; `canStop` in `AvailabilityControls`).

Peers can neither trigger nor undo it. A configured peer pause can be escalated locally to immediate.

**Router behavior.** For uncommitted (pre-output) attempts on the local node, `routing.go` `withdrawLocalIf` marks the attempt `redispatched/node-paused`, adds the node to `excluded` and redispatches under the same request owner. Committed attempts get `nativeCancelLocked(factNodePaused)`, which ends supported streams with an SC-a clean error and does not continue them seamlessly. Peers learn of the pause from the `pausedBy` inventory hint on a nominal 15-second scan. Until then the paused node's admission refuses with 503, and the origin router fails over (`docs/node-availability.mdx` "How peers learn").

**Against the owner's Halt (expectation 10):**

| Large, local-only button in the toolbar | Small `kind="primary" size="tiny"` "Stop local models now" in the self card and Routing settings, plus the tray item | Not in `AppBar`; naming differs; size |

External or adopted engines (Ollama app, LM Studio app) are refused, and the pause stays incomplete | "Force" for external apps was deliberately rejected (Q5). ### Q2: Engine on/off controls on node cards
- **Node card:** `NodeList/NodeEnginesInline.tsx` renders, for each reported engine:
  - a KUI `Switch` that calls `pairApi.engines.toggle(engineType, nodeId)`. Locally this is `toggleLocalEngine`: `engine:status`, then `engine:start` or `engine:stop` sent to the broker. For a peer it is `toggleRemoteEngine` through the relay (needs a management grant).
  - `EngineLockControl`, the padlock: local `engine:set-lock`; read-only "Locked" on peers.
  - `CredentialControl` (local only): an engine API key through `pairApi.engines` credential methods.
  - an "Install" button for engines that are not installed (`pairApi.engines.install`).
- **Engine settings (gear icon):** `NodeEngineSettings.tsx` renders `EngineSwitchControls` (E4 "Switch engine From/To") and one `BackendRow` per engine. `BackendRow` contains:
  - `BackendHeader`, with a second On/Off `Switch` (`handleToggle`, the same `toggle` command)
  - `BackendUpdateBanner`
  - `ModelSection` (models per engine)
  - `EngineSettingsSection` (built-in engines only)
  - `BackendFooter` (uninstall, local only)
- **Start-on-demand:** it exists only for saved-On engines (`wakesleep.go` `Wake`; proxy dormant candidate). The vault FORK.md line "Engines saved Off are never started on demand" still holds for ordinary wake (no FORK.md exists in the join33 worktree, while README.md is present there). The exception is engine bindings (engine-binding Tasks 1-8): `bound_engine.go` `runBoundEngine` → `activateBoundCold` starts a saved-Off, unlocked engine when an explicit `engineBindings` entry names the requested model. Roles (`Policy.Roles`, `{engine, model}`) do not imply a binding, so a role whose engine is Off is not started unless a binding also exists.
- **If the toggles were removed,** these would still need a UI:
  - install, update and uninstall
  - running, health and error state per engine (crash, external or adopted, termination unverified, "Pause incomplete" detail)
  - the credential/API key
  - port conflicts
  - a way to stop a misbehaving engine (or Halt covers it)

  The backend would also need wake to start Off engines for a role or profile, meaning the saved-On requirement in `Wake`, the dormant candidate and residency changes, or a role-to-binding derivation. Otherwise removing the toggles leaves engines that nothing ever starts.

### Q3: Multi-engine concurrency
- llama.cpp and Ollama/Strata can run at the same time: there is no exclusivity in engine-manager start (C14), and manual toggles are independent. Each engine has its own server port and proxy facade port (`enginesettings.Config.ServerPort/ProxyPort`).
- The **E4 switch** (`engineswitch.go`, `SwitchRequest{SourceEngine, TargetEngine}`) is a durable transaction: drain source, stop source with proof, start target, publish facade. It is for engine exclusivity or replacement (freeing VRAM, moving the facade), not for switching models. It is used manually from `EngineSwitchControls` and automatically by bound-engine activation.
- **One-active-engine assumptions:**
  - `runBoundEngine` (C13) treats every other running engine as the conflicting source. With exactly one, it switches it away; with more than one, it refuses. This directly conflicts with "multiple engines should be able to run when resources allow".
  - Admission residency: `Admission.MaxResidentModels` defaults to **1** and counts models resident on any engine (`admission.go` ~L659, `residency.go` L149). With `switchModels:true`, LRU idle models are unloaded through `admission/unload` to make room.

  So the "one resident model per machine" default lets several engines be running but serializes loaded models across them. It is configured in `node-policy.json` `admission.maxResidentModels`, and the desktop exposes it only through "Advanced policy JSON" (C16). `memoryBudgetBytes` is an alternative cap (0 = off).

### Q4: Per-engine settings content
`EngineSettingsSection.tsx` (accordion "Settings" inside `BackendRow`, built-in engines only) edits these `enginesettings.Config` fields through `engine:preview-settings` / `engine:apply-settings`:
- Server port and Proxy port
- Working-set limit (MiB, Windows)
- Engine arguments (`launchText`: args plus leading environment assignments)

It also shows `workingSetLimitStatus`, CORS restrictions (changeable only locally, `Executor.RejectRemoteCORSChange`), adopted/editable reasons and switch reservation. `Config` additionally carries `Serving` (typed llama/Strata prepared serving) and `ModelLoads` (per-model llama load settings, edited elsewhere through ModelSettings).

These belong to the engine process and must survive a move to per-model profiles:
- server and proxy ports
- environment such as CUDA PATH or `CUDA_VISIBLE_DEVICES` (inside `launchText`)
- the Windows working-set cap (a job-object limit on the engine process, `lifecycle.go` ~L595)
- CORS
- autostart (saved On intent and restore)
- the binary or install choice

Per-model candidates that should move to profiles: context, ngl, batch and the rest of the llama.cpp flags now living in `ModelLoads`/`Serving`, and any model-specific args in `launchText`.

Removal is medium-sized. It is mechanical except for the following:
- the activation-veto ordering (pause → lock) in `activationVeto`/`remoteVeto`
- the bound and residency reasons (`engine-locked`)
- the `-32013` error code across HTTP, ec wire, switch kind, TUI and desktop
- the `locked` key in `engine-state.json`

**Per-role gate:** none exists. `Role` is `{engine, model}`, and peers with a grant can edit roles through the policy relay. The nearest mechanisms are:
- removing the role
- `servedModels` (an allowlist of models a node serves)
- `localOnly` on a profile (C20): a lock against peer edits of generation settings that does not stop activation, and which the owner endorsed on 2026-10-28 ("inference lock stays generation-only"). It is distinct from the engine lock and can be kept.

A "lock a role" feature would need a policy field (for example `Role.LocalOnly` or `LockedRoles`) enforced in broker policy-relay merge (`policy.go` peer-relay handler) and possibly in proxy admission, if it should also stop serving.

## Mapping to owner expectations
- **E10 Halt:** the mechanism exists (immediate pause). Missing: toolbar placement, the name and size of the button, a force-unload policy for external apps (contradicts Q5), push-based peer notification, and a peer-reversible "simple on/off" (no such state exists; configured Pause is peer-settable but only locally reversible). Engine locks still exist everywhere; there is no role lock.
- **E6 no backend toggles, multiple engines:** the toggles exist in two places. Start-on-demand needs saved On, except for explicit engine bindings. Bound activation and the default `maxResidentModels:1` serialize engines and models. The E4 switch UI is exposed, which the owner considers meaningless.
- **E7 one node settings place:** per-node data is split across the card (engines, availability), the "Show engine settings" accordion (switch, per-engine settings, models), and Settings → "Routing & resources" (availability again, roles, bindings, model settings, advanced policy JSON).
- **E3/E4 profiles:** per-model launch knobs currently live in per-engine `Config.ModelLoads`/`Serving`/`launchText`, which need splitting (Q4).
- **E1:** card roles hard-code weak/medium/strong (`ROLE_TIERS`).

## What a fix would have to touch
- **Halt as specified: small to medium.**
  - Small: add a large local-only "Halt" in `desktop/src/ui/components/AppBar/AppBar.tsx` that reuses `useNodeConfigurationStore.requestAvailability(selfId, 'paused', 'immediate')` and the `AvailabilityControls` state; rename the copy in `NodeAvailabilityControls.tsx` and `tray.ts`; fix the stale comment in `node-policy.ts` and the gap in `docs/node-availability.mdx`.
  - Medium, optional: push a pause hint to peers instead of the 15 s scan; force-terminate adopted engines (needs an owner decision reversing Q5, in `wakesleep.go`/`lifecycle.go` `doStopOwnedContext`).
  - A peer-reversible "simple off" needs either a new availability flavor without the management fence (`availability.go` `setAvailabilityRequestAs`, `managementBlockedLocked`, `nodepolicy.PauseMode`), or reuse of per-engine Off. Medium; it touches the 2026-10-23 decision.
  - Reuse: `pauseMode` immediate, `pauseNode`, `pauseEnginesOn`, `withdrawLocalIf`. Do not add a second availability owner.
- **Removing engine toggles and locks: medium to large.**
  - Locks: medium, mechanical, about 60 source/doc files and about 35 test files (Q5); remove the `-32013` code end to end and keep the pause veto.
  - Toggles: small in the UI (`NodeEnginesInline.tsx`, `BackendHeader.tsx`), but they require a role/profile-driven activation. Either relax `Wake`'s saved-On requirement or derive engine bindings from roles/profiles (reuse `bound_engine.go` `runBoundEngine`/`activateBoundCold`), and replace "saved On" restore and idle-stop semantics. Medium to large.
  - Multi-engine: change `runBoundEngine` so another running engine is not a conflict when resources fit (and use the memory budget rather than `MaxResidentModels:1`); keep E4 for explicit replacement only, or drop it from the UI (`EngineSwitchControls.tsx`). Medium.
- **Collapsing per-engine settings into a per-node settings page: medium, mostly desktop.**
  - Create a node settings view that hosts `EngineSettingsSection` (per-engine process settings stay: ports, env, working set, CORS), `NodeAvailabilityControls`, and the `RoutingSettings` per-node sections (roles, bindings, model settings, policy JSON), opened from the card.
  - The backend RPCs (`engine:*-settings`, `policy:*`, `node:set-availability`) need no change.
  - Moving `ModelLoads`/`Serving` into profiles is a separate, larger change (other units).

## Open questions / not verified here
- Native timing and behavior of immediate stop: PC3 acceptance rows are all "untested" in the vault Todo.
- Whether the owner's Halt "force-unload" means killing external apps (Ollama.app, LM Studio): this conflicts with the accepted Q5.
- Whether the owner's peer "simple on/off" should be undoable by peers (that reverses the 2026-10-23 local-Resume decision for that level).
- Whether removing the engine lock should also remove `-32013` from the wire, or leave it as dead code: a pre-release decision allows in-place format changes.
- Whether peers' `pausedBy` hint latency (15 s nominal) is acceptable for "immediately stops offering". The node's own 503 covers correctness, but each router pays one failed attempt.
