# L6 — Memory estimation, telemetry, measured runs and qualification: what is landed versus planned, and how it maps to the owner's Estimate + Validate
Baseline: integration/join33 4eccd05d. Investigated: 2026-10-31.

## Verdict

**Estimate:** most of the engine side has landed. `modelEstimateState.estimate` prices weights, KV for dense, SWA, MLA, shared-KV and NextN layouts, recurrent state and compute workspace (MoE included) as ranges labelled with a basis. Each host, device or shared pool gets a fits/tight/exceeds verdict with "not priced" warnings, compared against fresh node-info telemetry. Users never see that verdict. The desktop `ModelMemoryEstimate.tsx` still recomputes its own strict "complete" rule, does not render low/high bands, and in practice always shows "Unknown". Auto (`modelAutoFit`) still demands a whole estimate with status `estimated`, which the estimator never produces, so production Auto cannot select anything. The frozen-Auto Apply check is the one remaining refusal based on an estimate.

**Validate:** effectively nothing exists. There is no `Measure this configuration` UI, no `engine:diagnostic-*` RPC, no measured-profile type and no exercise code. The only landed piece is a node-wide drain helper, `Broker.drainNode`, which only tests call. Speed is measured only passively by the proxy and is keyed per run. Unconfigured llama.cpp records no speed and no load buffers, and does not get the configuration key that stated or measured figures are bound to.

The diagnostic-run plan is a close match for the owner's Validate: consent preview, low and full context fill, speed plus memory, peers may request it, and untested profiles stay routable. It differs in three ways. Results are bound to exact files and build, but not to CPU or RAM identity. It warns only on "other GPU users", with no VRAM or RAM thresholds. It refuses on Pause, and Pause may not be the same thing as the owner's "Halt".

### 2. The estimate path today

Desktop: Model Settings → `ModelLoadSettings` "Preview model changes"/"Recalculate" → `engines:preview-settings`, plus `engines:inspect-model` (`ws-channels.ts:177,186`) → broker `client_requests.go:229` / `modelsettings.go:1235,1290`. The broker attaches `Memory: b.modelTargetMemory()` to the worker envelope. In the manager, `inspectModel` calls `modelMemoryContext`, which builds a `modelTargetMemoryOwner` from the node-info observation and maps the device through `mapModelSettingsDevices` with native init when permitted. `InspectModel` then calls `e.modelEstimates.estimate(ctx, advisory)` and `e.modelMemoryProfiles.attach` (stated records are shown, not overlaid). Preview goes through `modelsettings_load.go:1132`.

Inputs are bounded GGUF facts (`gguffacts`), artifact bindings, the compiled `ResolvedLoad` (finite context/slots/GPU layers), a build ID and the target memory observation. The output is components with `bytes/lowBytes/highBytes/basis`, domains per pool (`host`, `device` with UUID, or `shared` for UMA) carrying required/low/high, capacity, free and reserve, and per-domain `capacityFit`/`freeFit` with warnings. The estimate is per pool. A device pool needs a reviewed DeviceBinding or QA1's single-GPU assumption.

Auto: context and layer resolution live in `modelsettings_auto.go resolveModelSettingsAutoInput` (context candidates `modelAutoContexts` in 256-token steps, layer bisection or enumeration), reached from `modelsettings_load.go:440`. It is gated by the strict `modelAutoFit`, so it cannot succeed today (C10).

### 3. Memory evidence and qualification

- `memory_evidence.go` is unchanged and Ollama `/api/ps` only (C16). `memoryQualificationFile` is a fixed operator file. `recordMatchesCapture` binds to host, manager incarnation, engine run, launch digest, model digest and config epoch (C17). That is run-scoped: a restart invalidates it.
- Native buffer reports (T14) are parsed from llama.cpp load logs only in serving mode, which covers typed loads and presets with a prepared config. Unconfigured llama.cpp gets nothing (C18). Results are shown by `ModelLoadBufferReport.tsx` but do not feed the estimate (that is estimation Task 9).
- Binding comparison with expectation 11:
  - Model file: yes (artifact identities).
  - Engine build: yes (executable, library and environment digest in the configuration key; the plan's `MeasuredProfile.BuildPin`).
  - GPU: only as a device UUID when bound; manual GPU placement is `unbound-gpu`.
  - RAM and CPU: absent. Only the pool kinds `host`/`device`/`shared` are in the key. Capacity is read fresh from telemetry at compare time, not stored as identity.

### 4. Telemetry

node-info supplies timestamped physical pools (`noderec.MemoryObservation`: id, kind system/dedicated/shared, device aliases GPU-UUID/PCI/LUID, total/free with age; freshness `MemoryFreshMS = 5000`). The broker ages and expires observations (`telemetry.go`). The manager maps llama device order to physical UUID (`modelDeviceMap`, telemetry T3).

It is consumed only by model settings: estimate comparison, Auto, review currency and configuration pools (C19). Routing and admission do not use it. Admission uses declared `Profile.memoryBytes` (C20). There is no PAIR-side pressure guard during loads, and the Windows cap is a hard limit rather than a watch (C21).

Gaps against the owner's wording:
- The preview warns only on unexplained GPU use. The owner asked for warnings above low VRAM use and above half RAM use.
- The plan refuses on Pause. Whether Pause is the owner's "Halt" or the owner's peer-controllable "off" decides whether this conflicts with "off is ok".
- The plan frames the run as a fallback "when PAIR cannot estimate". Its UI (Task 9) does show it for any llama.cpp configuration with a key, so this is only framing.

### 6. Speed

`nvpair-proxy/performance.go` and `performance_extract.go` extract timings from llama.cpp and Strata streams (and Ollama) per request, keyed as in C22. The broker `performancestore` persists them and `NodePerformance.tsx` displays them. Because the key includes the engine run ID and the request options digest, history fragments across restarts and option changes. It is display-only. Unconfigured llama.cpp fails `performanceCurrentIdentity` for lack of a model digest (C23).

The diagnostic plan records its own speed inside `MeasuredProfile` (Task 3, read from `timings`) and does not write to the performancestore. Speed from a diagnostic run would therefore live only in the measured record unless a task is added to emit samples with the same key, or the plan is amended to do so.

## Mapping to owner expectations

- **#11 Estimate.** The engine side is mostly there (C8, C11). Three things stop it reaching the user: the renderer discards it (C12), Auto is dead (C10), and stated or measured figures are not overlaid (estimation Task 9). Coverage depends on the typed configuration (C15). Owner presets and unconfigured llama.cpp get weights-only estimates with no key.
- **#11 Validate.** Absent (C5, C6). The plan matches on phases, peers, consent and routability. It falls short on binding (no CPU or RAM identity), warning thresholds and the Pause/Halt semantics.
- **#3 Profiles.** Measured and stated records attach to the `configurationKey` of a node-local applied typed load, not to a copyable "profile". Copying a profile to another node yields a different key (different device UUID and source digest), so measurements do not travel. That fits "bound to node hardware".
- **#6 Apps vs engines.** Consistent: no Ollama/LM Studio estimation is planned. However, the only landed qualification producer (`memory_evidence.go`) is Ollama-only, which is the reverse of the owner's priority.
- **#10 Halt.** The diagnostic veto set is Pause plus per-engine lock. Engine locks are something the owner wants removed, so the veto set needs re-pointing once Halt/role-lock lands.

## What a fix would have to touch

**Estimate**

- *Small/medium.* Render the service verdict, ranges, basis and warnings in `ModelMemoryEstimate.tsx` and delete its `comparison()`/`complete` rule. This is memory-telemetry Task 6 plus estimation Task 12 (Run anyway, stated-figure entry using the existing `engines:set-stated-memory`).
- *Medium.* Make Auto use `CompareEstimate` (accept fits/tight, refuse only exceeds) and add Apply-anyway. This is memory-telemetry 5b with its amendments, touching `modelsettings_auto.go modelAutoFit` and `modelsettings_rpc.go:252`. Until then Auto is non-functional.
- *Medium.* Overlay stated and native figures onto the estimate (estimation Task 9 in `modelsettings_estimate.go`). Add typed `n-cpu-moe` (Task 10).
- *Medium/large, not planned anywhere.* Give preset-mode and unconfigured llama.cpp a configuration key and finite allocation (C15), or make the owner's profiles typed loads. Without this, owner presets get neither stated figures nor diagnostics.
- *Large.* Real calibration (Task 14), and the Strata provider (EMP 4–6).

**Validate**

- *Large.* Diagnostic-run Tasks 1, 2, 3, 13, 4, 12, 6, 7, 8, 9, 10, in that order. Reuse `drainNode`, `model-memory-profiles.json`, `modelConfigurationKey`, the switch relay pattern (`switchrelay.go`/`engineswitch.go`) and `modelsettings_reviews.go` for preview IDs.
- Hard entry conditions: estimation Tasks 9, 12 and 13 and telemetry 5b, 6 and 7 must land first, because Task 4 is reserved behind them.

**Amendments the owner's text implies**

- Add CPU model, RAM capacity and GPU model or VRAM to the `MeasuredProfile` provenance, at least as recorded facts rather than key inputs.
- Add VRAM and RAM in-use thresholds to the preview warnings.
- Decide whether peer-controllable "off" allows a run.
- Optionally emit diagnostic speed into the performancestore with a stable, non-run key.

## Conflicts between the owner's expectation and settled plan decisions

1. "Estimates, stated figures and observed overlays stay advisory: never admission authority, qualification, ME2 evidence…" (estimation plan). The owner did not ask for admission from estimates, so there is no conflict. ME2 QA2b offers a manual "Use this figure for the routing budget".
2. The labels "positive claims never say guaranteed or qualified" and "Measured on this machine" separate measurement from qualification. The owner's "validate … lock it to that model/build/hardware" is satisfied by the measured record. The word "validated" is just not used. Not a substantive conflict.
3. Diagnostic "A paused node never runs a diagnostic". This conflicts only if Pause is what the owner calls "simply off". The owner allows off and forbids Halt.
4. "Only the applied configuration is measured" plus a key only for typed loads (C15). Owner presets cannot be validated until they are typed or keyed.
5. "Node-wide exclusion: every engine drained, unload every model (QB2)". The owner did not object, but this is heavier than "check resources and confirm". It is consistent with the owner's consent step.
