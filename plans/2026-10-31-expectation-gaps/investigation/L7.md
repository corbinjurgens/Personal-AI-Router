# L7 — Routing: context-size gating, model-list advertisement, residency and warmth, and what the smart-routing plan leaves open
Baseline: integration/join33 4eccd05d. Investigated: 2026-10-31.

## Verdict

Context gating exists, but only for tier requests (`weak`, `medium`, `strong`), and it compares the request against hand-declared numbers: a candidate is dropped when its declared `contextTokens` is nonzero and below `len(body)/4` plus the requested output limit. A role with no profile declares 0 and is treated as unbounded. PAIR does not read back the real `--ctx-size` on the routing path; the launched context is verified only inside strict/hybrid qualification and resident loads, and only for native llama.cpp launches. The model list exposes no context field: a tier alias is `{id, object, created, owned_by}`, and a test pins that shape. The owner's model of user-defined roles is contradicted by the source: role and tier keys are validated against the fixed `nodepolicy.TierOrder` (weak, medium, strong). The smart-routing plan's scorer is keyed by tier rank and (host, engine, model), not by name, so it does not conflict with user-defined roles, but it inherits the fixed vocabulary, and it settles nothing about context advertisement, residency beyond keeping warmth as a hard class, or role names. Routing history records the requested tier and the served node/engine/model, but the desktop does not show the tier and nothing records the candidates considered, so expectation 12 is partly met.

## Findings

### 1. Context gating

- The rule is C1/C2. A candidate is kept only if it has every needed capability and either no declared bound or a bound at least as large as the estimate. The estimate is `len(body)/4` (bytes divided by four; it likely over-counts JSON syntax and image data) plus the first positive output limit found. No output reserve is added when the client sends no limit.
- Bounds come only from policy: `AdvertisedRole.ContextTokens` (a peer's role, copied from its profile in `Policy.Advertisement`) and `TierEntry.ContextTokens` (this router's own tier entries). `entryEligible`/`roleEligible` do not exist in the tree; the eligibility tests are inline in `resolveTierCandidates` (C1, positive control found).
- Nothing in discovery or the broker feeds a measured context into routing (C6, C8). Engine-manager does measure it (C7): after a native launch it reads `/props` for each loaded model and compares it with the envelope, then publishes the result as `ServingReadback.Observed` for the desktop only.
- The launched context is known to PAIR for native llama.cpp launches. The engine manager writes the preset `ctx-size` (C9), and a launch-validated envelope enters `EngineIdentity.Serving` (C10). Strict/hybrid admission uses that envelope (C11), and resident loads require profile context to equal it (C12). Ordinary requests use none of this.
- Enforcement point: the serving node enforces context only for strict/hybrid requests (C11, C39). Ordinary local admission (C13) does not check it, so an oversized request that reached the node is left to the engine. The router enforces the declared bound only for tier requests (C3). A concrete `model` request has no context check anywhere in PAIR (inferred from C3, verified by grep).
- Two gaps follow from the code. A role with no profile declares 0 and passes any context (C1, C4). And a profile that is not native-launched and not qualified has no launched-context evidence anywhere (inferred from C10 and C12).
- The 404 for an oversized tier request names only capabilities (C14), so the client cannot tell why nothing matched.

### 2. Model-list advertisement

- `serveModelList` (C16) returns upstream records unchanged for concrete ids and appends tier aliases only on the OpenAI dialect (C15). A tier alias carries no context or output limit, and a test pins that field set (C15). The alias record is the only thing a client sees for a tier.
- Neither OpenAI's `/v1/models` schema nor this repo's Ollama dialect carries a context field for an alias (C17). Ollama's per-model context is in `/api/show` (external knowledge; not in the repo). No field in this repo's model list carries context for a tier.
- The owner's wish (C37) needs a new field, and it has to be computed from `declaredRoles` (`self` plus `peers`) and the policy's tier entries, filtered by capability for that tier. Both inputs exist in `tiers.go` (`declaredRoles.forTier`, `tierModelEntries`). The max would be the largest declared bound, not the launched one, unless the real-context feed (section 1) is added first. The pinned test would need to change deliberately.

### 3. Candidate ordering

Quoted in CLAIMS (C20). Within a leading class, `reserveRoundPrepared` passes only candidates with equal `tierRank`, `warm` and `preparation`, so `candidateChoiceLocked` (C21) decides among them. Its load term is the proxy's own view (scheduler pending, GPU pressure, this proxy's reservations), so a request-sized term would have to enter there or in a scorer placed before it.

### 4. Residency and warmth

- `MaxResidentModels` defaults to 1 (C24). The owner approved that default in 2026-10-22's defaults bundle.
- A cold candidate becomes warm when it is admitted on its node (C25, C26). Admission evicts an idle resident (least recently used) or waits up to 30 seconds (queue timeout). A declared resident is loaded by `POST /models/load` through the engine manifest (C26). That an ordinary cold request is loaded by llama.cpp's own router on first use is inferred: the probe sends `autoload=false` (`serving_readback.go` line 83), which implies the default autoloads, and `load-on-startup=false` is set in the preset (`serving_llamacpp.go` line 927). Not run here.
- Two roles on one node with one slot: each (node, engine, model) is a separate candidate and nothing in the code couples them. With the default `preferLoaded: "tier"`, a weak request is ranked by tier, so it can go to a cold weak on a node whose medium is warm and evict that medium (inferred from C25/C27). Warmth beats cold only within the same rank.
- `preferLoaded` is applied only in the tier comparator (C27); concrete routing does not use it. `candidateChoiceLocked` does not consider warmth at all: it only sees the class already chosen.

### 5. What the smart-routing plan settles and leaves open

Settled (Decisions and "Decisions made while writing this plan"): the scorer is proxy-side and request-sized; the broker feeds speed evidence by a new private method; warmth, preparation and tier rank stay a hard leading class under both `preferLoaded` values; the scorer uses only the leading class; no energy term; no compatibility work; a `selection` record in routing history; evidence keyed by (host, engine, model); a 512-token output budget for the score when the request names no limit.

Left open or explicitly out: energy and power; memory headroom; cold fast node versus warm slow node (the plan keeps the warm node, and records this as a coverage limit the owner may veto); queue duration; model-content identity for unconfigured llama.cpp models (name-based measurement only, granting no strict or hybrid eligibility); scheduler changes; the owner's live acceptance (MSI orchestrator).

Context: the plan does not touch `contextTokens` gating (it keeps `requestNeeds.contextTokens` as is and adds `inputTokens`/`outputTokens`), and it does not add context advertisement or real-context readback. Expectation 5 is not in its scope.

Vocabulary: the scorer, evidence cache and `selection` key on tier rank and (host, engine, model), so it works if tier names change, as long as an ordering exists. The plan does not depend on the names, but it does depend on the ordering, because `tierSearchOrder` and `AllowStronger`/`AllowWeaker` define "stronger" by index in `TierOrder`. Its acceptance text and history enum (C29) use the three fixed names. There is no direct conflict with user-defined roles, but a role-name change would also touch `TierOrder`, the nine reserved aliases, `routingHistoryTiers` and `requestedDescriptor`, none of which the plan covers.

### 6. Routing history and expectation 12

What the desktop shows (C30 to C32): the table rows (time, requested model, attempts count, served node/engine or deployment/account, spend, reason, state). Expanding a row lists each attempt's destination, model, reason, admission and first-byte times, HTTP status and account state. The served node is therefore visible after the fact, and in flight through the `routing` state, along with reasons for failed attempts. The response headers `X-PAIR-Node`, `X-PAIR-Engine`, `X-PAIR-Model` and `X-PAIR-Tier` (C33) answer "where did this go" for the caller.

Not shown: the requested tier and mode (both recorded, C30; not rendered), the candidates considered, their order, why one was chosen, and any context or capacity term. The plan's `selection` object is the planned answer to this last gap.

Conclusion for expectation 12: met for "where did it go and why did the attempt fail"; not met for "why there" and for tier visibility.
