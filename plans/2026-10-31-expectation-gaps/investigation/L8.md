# L8 — Engines versus apps: Ollama/LM Studio footprint, Strata status, custom llama.cpp forks and option introspection
Baseline: integration/join33 4eccd05d. Investigated: 2026-10-31.

## Verdict
Three manifests are bundled (llama.cpp, Ollama, LM Studio). Strata exists only as a testdata template and in the prepared-serving code; it is not packaged, and any MSI-side standalone copy cannot be checked here. A custom llama.cpp build can be selected by a same-id override, but only through `detect`, because the launch binary is whatever `detect` finds and start refuses when it finds nothing. The engine manager has no engine-build identity: it never runs the binary to read `--version` or `--help`, the only build string it reads (`/props` `build_info`) is a diagnostic gate pinned to b11146, and load-time binding is a stat-and-sample digest of the file. The planned apps classification (`kind`, `AppsRow`) is absent. Ollama/LM Studio-specific code is about 1,200 non-test lines, roughly 2.6% of the root package, spread across dedicated files, per-family sections and family-keyed branches in shared files.

## Findings

**Manifests and overrides (Q1).** The three manifests use different runtime kinds. llama.cpp is a process with a router readiness probe and a fixed launch prefix (C2, C4). Ollama is a process with unpinned vendor downloads (C5). LM Studio is a command-mode daemon driven by the `lms` CLI (C6). Only llama.cpp pins its downloads (C3). Model listing differs too: llama.cpp reads `/models` and filters `status.value` for residency, Ollama reads `/api/tags` and `/api/ps`, LM Studio reads `/api/v1/models` filtered by `loaded_instances` (C2, C5, C6). No bundled manifest uses `memory_plan`, `detect_required`, `working_set_limit_mib` or `serving` (grep over `manifests/*.json`, no hits).

For a custom llama.cpp fork: place `llamacpp.json` with `"engine":"llamacpp"` in the per-user `engines/` directory (C8). Set `platforms.<host>.detect` to `["<absolute path to fork llama-server>"]` and `runtime.bin` to the same path (C9, C10). `detect` is the field that matters; `runtime.bin` alone does not select the binary, and start refuses when detect misses. The fork must answer `/props` with `role: router` or readiness fails (C2). Keeping `family: llamacpp` keeps the typed-serving and model-store paths (C11). Device enumeration and buffer diagnostics still refuse any build other than b11146 (C12, C13). A fork under a new id would need a complete manifest and `family: llamacpp`.

**Strata (Q2).** Strata is a dynamic engine. The facade is built from its `openai-chat` descriptor (C14, C15). Inventory and residency come from `/v1/models`, and load and unload use `/v1/load` and `/v1/unload` (C14). The prepared finite-serving adapter exists and is tested offline (C15, C16). The memory-plan translation is library code with no caller (C17). Open per the Todo: MSI native build identity, an owner-approved profile, an operational interval, and load, cancel, unload and peer-route evidence (C18). The vault status also lists `memory_policy` and `--expert-cache auto` / `--prefill auto` as unapprovable because the server resolves them from live telemetry, an inline `api_key` in preparation output, and a build without source or dirty identity (Todo context, 2026-10-28 status).

**Ollama and LM Studio footprint (Q3).** The root package has 46,532 non-test lines in 110 files. Code whose primary purpose is Ollama or LM Studio is about 1,200 lines, or 2.6%: `lmsget.go` and `lmsdelete.go` (303), their sections in `modellayout.go` (582, about 35% of that file), catalog parts (about 144), the Ollama memory extractor (about 60), the Ollama pull decoder (34), and family branches in `actions.go`, `wakesleep.go` and `pull.go` (about 90, approximate) (C35-C37). Their tests add about 920 of 82,445 test lines, about 1.1% (`lmsget_test.go`, `lmsdelete_test.go`, `linked_model_lmstudio_test.go`, `linked_model_ollama_test.go`). On the desktop, 33 of 323 files mention an app, and the app-specific pieces are the scrape script, the catalog, LM Studio credential and stale-model tests, the capability constants, and `CredentialControl` (C38). These are mention and span counts, not behavior.

**Build identity and option introspection (Q4).** Nothing reads options or a version from the binary (C19). Captured at runtime: slot context and count from `/props` (C20), and `build_info`, used only as a diagnostic gate for b11146 (C13). `ServingReadback` has no build field (C21). Load-time identity is `NativeBuildID`, a digest of size, mtime and a sampled hash (C22). Validation records therefore bind to file identity, not to what the binary reports. The memory qualification's `runtime.revision` is copied to provenance but never compared with a live build (C23). The owner's b11219 and b11985 builds are not in the repo (C25). The nearest existing source of a build string is `/props` `build_info`, already read in `serving_readback.go` and `model_buffer_capture.go`; the install marker and startup output carry nothing (C24). `build_info` is a runtime response, so it cannot identify a build before start.

**Launch text and extra options (Q5).** Per-engine extra argv is accepted without an allow-list (C26, C27); environment assignments become `launch_env` (C28). Per-model options are not free-form. A preset key must be one of 107 known keys (C29). 79 of those are refused as unsupported envelope-affecting options, leaving 28 unflagged keys, fewer after `models-preset` and `models-max` are refused (C29, C30). The parser does not keep unknown keys, and the typed writer rewrites the preset from typed sections (C30). This is consistent with the 2026-10-31 decision that preset short keys resolve only in `llamaPresetOptionKey`.

**llama.cpp install and own binary (Q6).** Install fetches pinned b11146 artifacts: CUDA builds for Windows and Linux (x64 and arm64), plain tarballs for macOS, no CPU or Vulkan variant (C3). Install is a no-op when detect finds a binary, and there is no update operation (C33). The owner's binary can be used through the Q1 override. The PC3 CUDA fix in the vault was a literal PATH in the launch environment (C28). Because values are not expanded, that literal replaces PATH unless it includes the existing value (inferred).

## Mapping to owner expectations
- **Expectation 4 (profile editor, introspected extra options, manual fallback).** Manual fallback exists (C26-C27). Introspection does not (C19). Extras are per engine and host-platform, not per profile (C27).
- **Expectation 2 (true identity).** Model naming and catalogs exist (C5, C6, C14). Outside this unit beyond that.
- **Expectation 6 (Ollama and LM Studio are apps).** In code they are engines: family branches in shared files, dedicated store and catalog code, command-mode daemon handling (C6, C35-C37). Classification is absent (C39).
- **Expectation 11 (validate bound to model file, engine build and hardware).** Model-file binding exists (C22) and memory qualification exists (C23). Engine-build identity does not (C21, C24, C25). Gap.
- **Expectation 12 (usable fork; Strata a future must).** Descriptor path and offline tests exist (C14-C16). Native acceptance and memory-plan wiring are open (C17, C18). Gap.
- **Expectation 3 (copyable profiles).** No profile object in the engine manager; settings are per engine (C27, C28). Noted only.

## What a fix would have to touch (files/owners; rough size)
- **Engine build identity (small to medium).** Reuse `/props` `build_info` from `serving_readback.go` `llamaServingPropsObserved` and `model_buffer_capture.go` `modelBufferReadProps`. Persist it in `shared/engines/serving.go` `ServingReadback` or the engine status, and bind it next to `NativeBuildID` in `modelsettings_load.go`. A pre-start identity would need a new bounded exec through the `proc.go` managed-process path (medium, new capability).
- **Option introspection (medium).** Parse `llama-server --help` through a new bounded exec in engine-manager. Reuse `llamaServingOptions` and the `launch.go` arity table rather than a new flag table (MANIFEST rule). Unknown forks already pass argv through (C27), so discovery would add UI and validation, not launch behavior.
- **`kind` classification (small).** Per the Todo: manifest field in `registry.go` and `manifest.schema.json`, `Manifest.descriptor` in `descriptor.go`, `shared/engines/descriptor.go`, and the TUI and desktop decoders. No code exists yet.
- **Strata completion (medium to large).** Construct `memoryPlanInput` and `strataMemoryPlanBinding` in `memoryplan*.go` and assign `Estimate.MemoryPlan` in `modelsettings_estimate*.go` (memory-plan Tasks 4-5). Reuse `compilePreparedServing` and `prepareStrataRequest`. Native acceptance is operational, not code.
- **Ollama and LM Studio (footprint only; the orchestrator decides).** Scope is C35-C38. Any change touches family branches in `actions.go`, `wakesleep.go`, `pull.go`, `memory_evidence.go` and `modellayout.go`, plus model copy, catalog and credential behavior.
