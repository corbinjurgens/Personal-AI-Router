## Goal

Qualify the OpenCode Chat Completions shapes the MSI daily strong-tier target needs: tools including history-only empty definitions, and automatic reasoning replay under the proposed owner-approved qualification boundary. ## Decisions made while writing this plan

- Preserve the existing structured modes under explicit, mode-specific qualification rather than remove current behavior or add modes based on assumed OpenCode use. Inventory controls which client fixtures claim to represent emitted structured requests. This is a plan-time interpretation of the review's preserve-existing-behavior requirement, not an additional owner answer.
- Use a required `shapes` object with required `tools` boolean, required `structuredOutput` array of qualified mode names (`json_object`, `json_schema`) and required `reasoningReplay` boolean. An empty mode array qualifies neither mode. Include replay in the coordinated revision because native automatic replay is source/synthetic-proven; local real-template qualification is a separate rollout gate. No effort/parallel booleans. The replay portion awaits the owner decision below before Tasks 2–6 execute.
- Coordinate the final schema revision once after NE's accepted join: use NE's agreed combined incompatible revision when it already includes B's exact contract; otherwise advance the accepted NE artifact version by one. Record the resulting exact integer and schema in Task 1's report before Task 2 starts. Do not hard-code an independent version 2 migration over NE.
- Accept non-null `tools:[]` as no active definitions, retaining the array unchanged and charging zero tool-definition overhead. Omitted tools has the same shape requirement. `tool_choice` absent, `none` or `auto` does not require active definitions; `required` and named choices require a nonempty tools array. Nonempty definitions, requiring choices, assistant tool calls and tool-role history require tools evidence; empty tools alone does not. Account accepted choices by the existing string/compact-object rule. History still requires tools evidence even with `tools:[]`. Preserve optional parameters and reject null/wrong-type shape members. This resolves native history-only compatibility without a general scalar/null cleanup.
- Proposed replay decision (owner approval pending): qualify and forward inbound assistant `reasoning_content` unchanged for local targets with exact NE-bound template/reasoning-format evidence and `reasoningReplay:true`; do not strip it. Count UTF-8 bytes plus the existing message/template overheads, including zero bytes for an empty string, and prove bounds independently. Unqualified/null/wrong-role/wrong-type replay still fails before effects. Blanket refusal would break subsequent native turns whenever a local reasoning model returns replayable reasoning; stripping could change model behavior and bypass the preservation/accounting contract. Local target use and real evidence remain unverified, so do not claim working local multi-turn compatibility yet. This visible expansion from refusal needs the owner's answer; Tasks 2–6 wait for it, without inventing a client replay-off configuration.
- A structured routing capability requires evidence for both existing JSON modes, because the shared capability has no per-mode granularity. A profile with fewer qualified modes can serve those modes only when it does not advertise the broad structured capability. Empty capabilities impose no extra shape requirement; vision/embeddings never install through this text-only contract.
