## Verdict

The remaining I tasks are internally consistent with the code they will replace, and the landed seams (registry, identity, cancellation, buffers, public lifecycle hooks) are where the plan says they are. The strongest objections are not inside any single task's logic; they are (1) a lifecycle hole no plan owns, namely open local-origin workloads of a proxy run that died without draining stay "running" forever at their own origin and cannot be cancelled (RED-1); (2) the cross-plan file-ordering ledger, which makes the daily milestone's residency (SR 5c) and pause-skip (PA Tasks 1-2) work wait on non-milestone work (G3, I5 hybrid selection, I6); and (3) scope inside I Task 5 and I Task 4b that the milestone does not need (hybrid listener cutover, peer interruption trailer channel, public selection). Five amendments at the end reorder or split work without weakening any landed safety boundary.

## Findings

### RED-1: a proxy run that dies without draining leaves its local-origin workloads "running" forever, uncancellable, and no remaining task retires them

- Claimed invariant (owner milestone, common brief): "honest completed/failed/cancelled outcomes including interrupted streams" and "headless service with Windows service-process restart". I plan Compatibility: "older displayed workloads lacking a run remain displayable but cannot be cancelled." I Task 7 Do: "Cover broker/proxy restart ... late old notifications/cancels ... Prove uncertain holds remain held and no automatic restart replay occurs."
- Code path (VERIFIED):
  - Terminal workload events for a local-origin request are emitted only by the request's own handler: `P/http_handler.go:937-962` (`emitTerminal`, inside `terminalOnce`) from the disconnect watcher `:980-986` and the finalize defer `:1077-1105`. The graceful path works: broker stdin EOF ends `readLoop` (`P/proxy.go:1365-1376`), `Run` cancels the serve context and shuts down within three seconds (`P/proxy.go:457-492`), and the facade servers use that context as `BaseContext` (`P/facade.go:572,578`), so every handler's `r.Context()` fires and emits "cancelled". During a supervised stop the broker still forwards the retiring process's notifications, because `stopProxySupervisorLocked` retires the policy incarnation first, then waits in `sup.Stop()`, and only then clears the process handle that `forwardProxyNotificationFrom` compares against (`B/proxy.go:458-470`, `B/proxy.go:199-203`).
  - A crash (panic outside `handleMessage`'s recover, OOM kill, external kill, `SIGKILL`) emits nothing: the supervisor's monitor loop respawns the worker and has no workload hook (`B/supervisor.go:239-300`); the only inferred-terminal producers in the broker are `failWorkloadsForNode` (a remote node leaving discovery, `B/workload_projection.go:652`) and `failStaleForeignWorkloads` (remote-origin records only, `B/workload_projection.go:740-742`). No code path retires local-origin records of a departed run (search for `failWorkloadsForNode(b.nodeID`, `proxy-exited`, or any local-origin terminalizer: none).
  - The replacement proxy mints a fresh 128-bit run (`P/routing_identity.go:13-18`); every cancel path requires the record's run to equal the current run (`P/request_registry.go:108-118`, `:121-131`; broker relay carries the record's run, `B/workloadcancel.go:27-37`), so the old records answer `found=false`/not_found for the rest of the broker's life. They are also re-asserted to a restarted workload-manager as active (`B/workload_projection.go:245-263` `rehydrateWorkloadManager`; `B/worker_lifecycle.go:455-459`), which keeps peers' silence sweep from retiring them either.
  - A whole-service (broker) restart is clean: active records are never restored from disk (`B/workloadstore/persistence.go:17-19`). So the hole is the proxy-only crash/respawn case, which the supervisor exists to handle.
- Observed result (INFERRED from the code above, not executed): after a proxy crash mid-stream, the origin's own desktop/TUI shows the job "running" (or "queued") indefinitely; cancel returns ok=false; the scheduler keeps counting it as pending work on `scheduledOn` (the very ghost the finalize comment at `P/http_handler.go:1000-1006` was written to prevent for the upstream-died case).
- Affected state: broker workload store (local-origin active records), scheduler pending counts, workload-manager anti-entropy set, desktop/TUI job cards.
- Why RED: the absence is proven from code and the consequence is deterministic; it violates the milestone's honest-outcome requirement for the restart case the milestone names. It is not an I-only defect: no remaining I, J, PA or SR task reserves it (J retires only its own presentation records, "retire only its open presentation records failed/proxy-exited", J plan line 102, not Workload records).
- Disposition: amend plan (corrective to the milestone; new broker Files, so coordinator reservation): when the policy runtime's acknowledged `runID` changes or the incarnation is cleared (`B/policy.go:1483`, `B/proxy.go:458-470`), retire every open local-origin record whose `RunID` is not the current run with an inferred terminal "failed: proxy exited", using the same provenance path as `failWorkloadsForNode`; add the assertion to I Task 7's `TestUnifiedDispatchProcess` restart case ("departed-run records reach a terminal state; the replacement's run cancels nothing of the old run"). Do not resurrect or replay them (consistent with "no automatic resumption/replay").

### UNVERIFIED-1: the half-open-client write deadline that 4b/5 rely on for "cancelled" classification fails its unit test in this container

- Claimed invariant (I Task 5 Do): "Process shutdown cancels owners/closes bodies and interrupts stalled downstream writes within the existing three-second grace"; finalize classifies a dead client by `committedSC.wroteErr` (`P/http_handler.go:1086-1094`), armed by `idleClientWriteTimeout` 30 s (`P/http_handler.go:293`).
- Probe: `go test -count=1 ./...` in `P/` (record below). `TestHandleHTTP_RealSocketFlushDeadline` failed: "workload never terminated after the client stopped reading (flush path not deadline-aware)" (`P/zombie_test.go:516`).
- Observed result: the fixture writes 1.5 KiB every 2 ms (`P/zombie_test.go:450-461`) and waits five seconds; this container autotunes loopback receive buffers up to 32 MiB (`/proc/sys/net/ipv4/tcp_rmem` = 4096 131072 33554432), so roughly 3.7 MiB written in five seconds never blocks the server's flush and the deadline never trips. On hosts with default buffer sizes the landed history reports this test green. The failure is attributed to the environment, but the attribution is inference.
- Affected state: terminal classification of dead/half-open clients (workload "cancelled" with "client connection lost").
- Disposition: defer; rerun the proxy module on Mac/MSI as the plan's whole-module gate already requires. If 4b changes the sink's write path, keep this test and consider a fixture that fills a bounded socket buffer (`SetWriteBuffer`) rather than relying on kernel defaults.

Between them the discovery watcher can `abandon` (`:1529-1531`) and a regenerate can `abortForRedispatch` (`P/cancel.go:46-54`), and both produce `retrySignal{}` (`:1646-1660`), so the next candidate is sent the request after node A produced output. ### LOW-7: the proxy's lease rejection is one undifferentiated error, so G3 cannot tell "binding mismatch" from "not ready"
